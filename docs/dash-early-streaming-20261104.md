# Early live-DASH segment streaming, UDM 1.37.0

The live planner previously rejected addressing with availabilityTimeComplete=false and discarded incomplete BaseURL alternatives. The resource reader already consumed HTTP bodies incrementally without requiring Content-Length, but those paths could not be reached from this live availability mode. Simply removing the rejection would also leave close-delimited response ambiguity and per-alternative transport policy unspecified.

[DASH-IF's current low-latency guide](https://dashif.org/dash.js/pages/usage/low-latency.html) describes early segment requests with chunked delivery as the server produces media. [RFC 9112 sections 6–8](https://www.rfc-editor.org/rfc/rfc9112.html#section-8) distinguish explicit message framing, truncated bodies and closure-delimited responses. Those public references inform this transport implementation; they are not evidence of IDM's private algorithm or of a current successful UDM recording.

The planner now evaluates early whole-segment alternatives at the existing end-time-minus-availability-offset boundary, preserving buffer-depth, Period and synchronized-clock checks. Each planned segment identifies which of its eligible canonical request URLs needs streaming framing. If the same canonical URL is also declared completely available at this instant, the complete-location policy wins. Canonicalization now matches the existing request-list URL construction, avoiding spelling differences between eligibility and dispatch. Clock-uncertainty intersection removes streaming entries whenever it removes their request URL.

Track workers pass the per-location policy into the resource store. That mode follows the original alternative through redirects, while each redirect still obtains its own origin-scoped headers. Early responses reject multiple Content-Length/Transfer-Encoding values, conflicting length and coding, invalid/empty length and unsupported transfer coding. An unknown-length HTTP/1 response must be chunked. HTTP/2 or HTTP/3 uses its stream framing; a declared length is still enforced. Content-Length and Transfer-Encoding are not accepted together. Normal complete-resource requests retain their existing policy.

The reader continues writing bounded temporary files as data arrives, accounting network bytes through the existing callback. It waits for the transport to report body completion, checks declared length when present, flushes, hashes and publishes the resource plus protected receipt. Read failures/cancellation take the existing cleanup path without committing that temporary response; completed resources on other tracks remain reusable. Successful transport end is the completion contract here. UDM does not independently prove a server's declared media duration or authenticity of its segment contents merely from valid HTTP framing.

WinHTTP and the explicit-proxy curl path perform HTTP dechunking/stream completion and error propagation. [Microsoft documents WinHttpReadData's asynchronous completion and error contract](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/nf-winhttp-winhttpreaddata). The curl adapter's buffer-drain loop calls its terminal result check before returning end-of-body, including interrupted-body errors. Actual missing chunk terminators, HTTP/2 resets, proxy behavior, cancellation timing and network stalls still require the deferred runtime tests; source inspection is not proof that every platform fault surfaces as expected.

Streaming policy is a request property, not a new media-content identity. Receipt hashes and segment bindings remain the existing whole-segment contract. Reconciliation can recover a completed receipt after a crash before the recording journal was promoted. Interrupted temporary segments are refetched in full; individual CMAF chunks are not checkpointed or salvaged. Existing idle timeouts, segment size bounds and worker concurrency still apply. This is a download/recording transport path, not a low-latency media player or ABR implementation.

Growing shared resources remain excluded. A byte-range or version-bound segment cannot use an incomplete alternative. If a representation still has a fully available alternative, existing complete-resource handling can use it; otherwise it reports the remaining append-aware recovery requirement. Strong entity-tag/size checks are not weakened. Initialization handling, signed browser request/credential scopes, DRM rejection, output assembly and publication checks retain their existing behavior.

The existing SegmentList capture binder versions every listed media resource, including whole-file entries. The planner classifies those as shared before version discovery, so an unusable early alternative cannot preempt waiting for a supported complete alternative. The current early capture path targets unversioned duration/timeline SegmentTemplate files; this increment does not claim early SegmentList/SegmentBase support.

The browser already supplies live representation selection and the native backend fetches the full MPD; no browser source changed, so extension 0.63.85 remains current. Runtime tests, browser handoff, conforming/nonconforming streaming servers, multiple qualities/tracks, stop-and-save, recovery, final playback and IDM comparison remain deferred. Installer creation, installation and publication are also deferred. Full parity and individual-chunk recovery remain incomplete. See [source evidence](reference/dash-early-streaming-20261104.json) and [build receipt](validation/dash-early-streaming-build-20261104.json).

Both production-only build passes completed with exit code 0. Final source review between passes moved listed-resource classification ahead of version discovery to preserve complete-alternative waiting. The receipt retains the initial snapshot/log and the corrected final snapshot/log. All five final binaries (UDM, NativeHost, Monitor, SetupHelper and Automation) report 1.37.0; their sizes and SHA-256 hashes are recorded. The final recorded source hashes remained unchanged during the final pass. This is compilation and artifact verification, not runtime streaming acceptance.
