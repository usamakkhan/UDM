# Responsive main-window Close policy — UDM 9.40

UDM 9.40 / source extension manifests 0.73.4 fixes the initial settings wait when closing the main window. It does not remove every wait in actual Exit or establish IDM parity. An additional legacy menu suite fails its queue-view check after 58 assertions; this remains unresolved and is excluded from passing totals. The initial current-build GUI run also hit an unexplained 400 ms aggregate watchdog; three unchanged-binary repeats passed. That variation remains open and is not relabeled as fixed.

## Measured cause and implementation

The 9.39 reproduction opens the real main window and holds Manager on a separate writer. Its 400 ms safety watchdog expires before Close returns: the observed handler time is 398.42 ms, and the assertion that the writer remains held fails. The fixture deliberately releases through its watchdog to avoid leaving a hung process. This is an isolated source reproduction against all frozen qualified 9.39 inputs and core hashes, plus the new UI fixture; it is not an installed IDM timing comparison.

A new MainClosePolicyTask owns a cancellable policy read. Close first tries immediate acquisition. If unavailable, it starts one reader and returns to the native message loop. The worker waits in short cancellable intervals, reads only the current CloseToTray value after command ownership clears, releases Manager and publishes an owned result. The GUI consumes it through the existing identity-scoped wake or timer. Repeated Close clicks retain the same owner. A fresh tray setting hides the main window; a fresh non-tray setting continues actual shutdown once. Read failure leaves the app available for retry.

Show app and explicit commands cancel pending policy reads. Show cancels without waiting for the busy model and cannot be followed by a stale hide. A blocked automation review is retained for timer retry instead of dropping its only wake. That review releases its acquisition lock before opening its modal UI.

The first implementation still blocked: showStatus displayed a waiting message, resized the window contents, and toolbar/category layout synchronously reread settings. Its preserved failed run took 419.29 ms. Layout now takes a nonblocking settings snapshot; if unavailable it keeps the controls' already-rendered visibility. Fresh available settings are applied on the next successful layout. This fallback concerns geometry only: Close never guesses its tray policy from stale settings.

Next classify the legacy menu queue-view failure: drive nonblocking refresh to its completion and retain evidence of the actual cohort before deciding whether a production fix is needed. The old suite also assumes synchronous command completion; do not force the app to block to satisfy those assumptions.

Actual Exit still synchronously captures/saves layout, joins update/model/presentation workers, stops integration/preparation, settles resume/authentication/progress commands, stops Manager, and joins icon/file-status workers. The policy-read fix deliberately preserves those lifetime guarantees. Moving the entire chain to a detached thread would risk accessing destroyed windows or Manager.

Next, measure those stages separately; split GUI-only control capture from background settings persistence; close admissions and signal cancellation while retaining Manager and HWND owners; poll command/worker readiness before joining; perform final GUI cleanup only after commands settle; then destroy the main frame. Progress command settlement currently updates native controls and must remain on the GUI thread. Validate cancellation, accepted-command recovery, explicit Exit during a pending tray decision, automation reactivation, update/network shutdown, and process lifetime before changing that chain.

Installed browser capture, owner/minimize/multi-monitor behavior, completed media downloads and actual IDM comparisons remain separate work. These checks cover the declared suites, not the entire backend registry or full inside/out parity. The original goal remains open.
