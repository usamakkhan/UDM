# Native DASH resource storage and receipts

The DASH module now provides a bounded resource downloader with durable verified receipts. Media bindings include a presentation digest, Period/adaptation/representation IDs, declared format, timeline mapping, sequence number, media time and duration. The presentation digest incorporates the original manifest request, declared root ID and availability origin. Live-to-static rematching retains the existing recording identity. Expiring segment URL query tokens are not part of the media binding.

Resource files and receipts use hashed names. Existing receipts are decrypted and checked against the requested binding, file size and SHA-256 before reuse. Invalid or missing receipts do not make a file complete. New downloads use a temporary file, require a nonempty complete HTTP 200 response, check Content-Length when present, reject unexpected content encoding and HTML content types, then hash and atomically publish the file. The encrypted receipt is written afterward. A crash before receipt publication leaves an uncommitted file that must be fetched again. This reuses UDM's hashing, encryption and atomic-write primitives; HLS-specific sequence/playlist state is not repurposed as DASH state.

The implementation supports up to 32 resource alternatives, six requests per redirect chain and 256 MiB per resource. It rejects HTTPS downgrades, strips explicit headers and browser/site-login context across origins, and checks paths for redirection before writes. Cancellation propagates through network reads and hashing. The optional byte callback lets the recorder apply its existing quota/rate accounting and progress updates. Callers must serialize writes for the same binding and use a job-owned working directory. Per-resource retries, backoff, captured credentials for alternate origins and aggregate scheduling remain recorder responsibilities.

## Integration limits

This helper performs resource downloads when called, but the running job engine and browser admission are not yet connected to it. Initialization resource binding, persistent recording indexes, segment overlap/replacement validation, Period transitions, muxing and final publication still need integration. A matching local receipt proves saved bytes match their recorded hash, not that a server has never changed content at the same logical segment identity. Source validators/refresh policy and actual media verification remain required for complete recovery behavior.

Runtime and regression tests remain deferred at the user's request. No media was downloaded during this implementation. Production compilation and packaging are recorded in `validation/native-dash-storage-build-20261028.json`. Browser 0.63.61 is unchanged. The candidate remains unsigned, uninstalled and unpublished; full IDM parity is not established.
