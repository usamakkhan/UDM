# Responsive batch acceptance — UDM 9.33

UDM 9.33 / source extension manifests 0.72.97 removes the synchronous queue-policy and admission/save/start work from the batch OK handler. In 9.32, the handler locked Manager for policy/default identity, opened queue selection and called offerDownloadBatch and startQueueForDownloads directly on the window thread. A busy catalog or durable save could stall its controls and painting.

## Ownership and behavior

The handler captures selected row identities, destination/category rules, descriptions and complete request context into BatchAdmissionDraft. Each entry retains headers, proxy route, website session, source page and media data. An owned cancellable BatchPreparationTask reads current queue-prompt policy or the browser's primary queue on its worker. Prompted imports prepare stored names and display labels in one cohort. Browser batches preserve their no-extra-prompt behavior; suppressed import prompts skip unused selector work. The shared primaryDownloadQueueName helper moves from Ui.hpp into QueueLabels.hpp with unchanged selection behavior.

During preparation the dialog freezes its existing interactive controls and continues pumping, while Cancel and window close remain available. The task never changes jobs/settings/catalog or claims an accepted-command guard. Cancellation wakes acquisition, and teardown joins its worker without waiting for an external Manager writer. Another accepted command defers this advisory read rather than losing its guard.

A prompted import opens the real queue selector using its prepared cohort, with no second model read. Queue-selection cancellation restores the batch draft. The parent pulse defers metadata changes and repeat actions during preparation, nested selection and accepted saving; the captured selection and request values remain owned.

Acceptance delegates to the existing FileInfoDecisionTask command owner. The worker calls applyBatchAdmission with an owned draft, then the unchanged canonical offerDownloadBatch and optional startQueueForDownloads methods. No window pointer or editable row is borrowed by that worker. It preserves queue/category validation, browser session/proxy ownership checks, duplicate/restart handling, transactional rollback and durable catalog publication. A queue-start failure after a successful save returns a warning and retains the admitted batch.

Once accepted, repeat OK/Enter and Close cannot duplicate or abandon the command. Controls including Cancel remain disabled while Saving downloads is displayed, and pulse/paint keep running. Success unchecks the captured rows and ends the dialog; the accepted guard remains held until DoModal returns and the joined task is released. Failure consumes the worker result, joins/releases ownership, restores the exact previous enabled states and selected rows, and shows the canonical error inside the dialog. Another click captures a fresh draft and retries. Browser status uses the existing instruction area; ordinary imports use the unused footer space, without changing dialog dimensions.

## Preliminary checks kept separate

Before the native input freeze, a preliminary backend run stops at 30 assertions because its partial-admission fixture expects Invalid while the canonical URL parser reports Use a complete HTTP, HTTPS or FTP URL without credentials. Correct that test expectation; the corrected preliminary backend passes 40 assertions.

The first standalone UI compile also exposes harness integration errors: diagnostics collides with an existing function, the local HTTP fixture URL helper expects const char*, and readBrowserProxy needs its owning header. After those corrections, a zero-assertion UI run exposes missing Winsock initialization before creating the local origin. Add the same explicit socket lifetime used by the existing authentication UI fixture. The corrected preliminary UI run passes 108 assertions and all ten complete-file comparisons.

Those preliminary checks use 9.33 sources with qualified 9.32 core binaries. They are explicitly excluded from current-build totals. Preserve failures, corrections, input inventories and linked hashes separately; only the newly compiled/linked 9.33 executions count above. No superseded release or installation is implied.

## Cleanup and next work

Removed 32 owned fixture/compiler roots and 34 temporary build files (332.5 MiB logical bytes), retaining assertions, diagnostics and hashes first. Current products/required cores, qualified 9.32 products, installed 8.68 / extension files 0.72.32, both personal catalogs and shared media tools remain intact. No media helper is copied. [Cleanup](validation/batch-admission-9.33/cleanup.json) and [preservation](validation/batch-admission-9.33/final-preservation.json).

No installer, installation, commit, push or release is included. Batch initialization still reads settings, categories and queues before its controls are ready, and refreshing all metadata rereads preview settings on the UI thread. Row request/header preparation and credential operations also remain on that thread. The new import fixtures finish ordinary metadata before their first OK click, so they do not establish how submitted default selections react to late metadata after queue-selection cancellation or a failed save; explicitly cover that row-intent boundary next. Move the initial settings/category/queue cohort and preview policy into an owned cancellable preparation path, keeping usable loading controls and stable row identity. Preserve user edits when late metadata arrives, keep media request context scoped to its row, and verify close/retry under a held Manager writer before new installed browser/IDM comparisons. Exceptional teardown, remaining Main/modal/shutdown paths and the wider feature/parity backlog remain open. Full parity remains unproven.
