# Responsive File Info action preparation - UDM 9.30

UDM 9.30 / source extension manifests 0.72.94 moves Start's session-refresh check and Download Later's queue-prompt policy read off the File Info window thread. The existing queue selector could also read names and labels separately while opening; File Info now supplies both from one prepared cohort.

A strong selected download is checked against current catalog membership on an owned advisory reader. It reads the session flag and prompt policy under Manager, preparing queue names/labels only for an enabled Later prompt. Start never prepares unused queue data. The dialog keeps pumping while inputs and repeat submission are frozen; Cancel stays available. Errors are inline and another click retries from current state. Advisory cancellation is drained by the existing owned cancellation command, and normal/exceptional teardown joins the reader. Notification occurs after publication and cannot undo it.

A successful Start preparation routes a rejected media session to the existing File Info recovery dialog or captures the draft for the existing accepted decision worker. A successful Later preparation either bypasses the selector or opens it with immutable names/labels. Queue selection cancellation leaves File Info open; an accepted selection still saves on the canonical worker. The prepared selector path does not query Manager. Generic callers without a prepared cohort retain their existing behavior.

The preparation snapshot is advisory, not a reservation or a transfer authorization. It writes no settings, job, catalog or accepted-command guard. Canonical Start/Later retain their backend validation and final request handling; another command's guard is never cleared by read cancellation. Input locking and parent polling suppression prevent overlapping GUI actions during preparation and nested selection/recovery. Initial prefetch and preview lookup are deferred while an action owns preparation/completion, avoiding competing lookups at this boundary.

## Validation

Five optimized products report file/product version 9.30, with 609 frozen repository inputs and source Chromium/Firefox manifests 0.72.94. Eleven backend suites pass 570 assertions across twenty-two C:/D: runs, including 17 action-reader assertions per drive. The earlier candidate's 17-assertion preflight is retained separately and excluded from those totals. Checks cover policy/session freshness, coherent labels, skipped queue work, non-mutation, cancellation under a real writer, guard isolation, missing membership, retry and throwing notification.

Owned Win32 controls pass 831 Main/Options, 257 pending File Info, 327 presentation, 46 first-paint and 239 wizard assertions (1700 UI assertions). Seven new actual-control cases cover Start, Later with/without prompting, queue-selector cancellation, read cancellation, failure/retry and rejected-session recovery. A real writer holds Manager before the Start/Later click; the handler, pulse and paint return, with Cancel available and no accepted save guard yet.

For prompted Later, a second writer acquires Manager after the snapshot and before the result reaches the window. The real selector opens and paints with its prepared labels while that writer remains held. Accepted Later stays owned and paintable until the writer releases. Start and retry download the complete expected authenticated fixture with exactly one request each. Advisory/selection/recovery paths issue no request to that fixture. The real media-session recovery dialog exposes no Resume action, intercepts its owned page launch rather than operating a personal browser, and returns to File Info on cancellation.

No personal desktop or browser was controlled. Owned test desktops were not switched to or given physical user input. These are targeted responsiveness/correctness checks, not a new installed browser/IDM timing comparison, complete backend-suite qualification or proof of full parity.

## Superseded candidate

Its Main run stops after 520 assertions, including two failures: the session fixture cancels recovery before observing the queued page-open callback and then requires that callback to have occurred; its final owner/workflow check also fails because it retains that assertion error. The six earlier new action cases pass. The fixture also compared the recovery URI with a bare page, omitting its required binding fragment. Intermediate 9.29 / extension 0.72.93 builds and passes 570 backend checks, but its UI compile is stopped before execution when source inspection exposes that incorrect expectation. 9.30 waits for the intercepted event and validates the exact base page, a 32-character hexadecimal session-binding token and saved video format v137 before cancelling. It records per-case diagnostics. Production action code is unchanged from 9.28 apart from version constants. Preserve the original build, backend and Main failure separately; this candidate was not installed or qualified.
