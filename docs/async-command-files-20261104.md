# Background command file checks — UDM 1.42.0

Version 1.32.0 moved file checks outside its manager-lock scope, but still called filesystem regular-file queries on the window thread while drawing command availability. ZIP preview and Recycle downloaded file could therefore delay a menu on slow, disconnected or heavily loaded storage. This increment moves that advisory query phase to a shared-state background worker. It does not move actual ZIP reading, recycling or every remaining synchronous UI operation off the window thread.

AsyncFileStatus owns a single detached worker and shared state. Each request owns an immutable sorted unique path vector. There is at most one active batch and one replaceable pending batch, rather than an accumulating queue of selections or per-path threads. A path-set change advances a generation; the worker checks it between filesystem calls and publishes results only if that generation is still current. The UI reads an immutable shared result without copying its file map. No manager/job/window pointer or window handle is captured by the worker, and no filesystem probe runs while its request mutex is held.

The same current path set refreshes at most once per second when no matching batch is already queued or active. Selection-state notifications post one coalesced prewarming message, avoiding a full probe request for every notification during Select All. Normal toolbar refresh includes the two file-dependent commands, warming them before a later menu opens. Non-file conditions, including completion/activity, selection count, extension and FTP-only predicates, still use the current detached command decisions. Files are deduplicated within a batch; disabled/irrelevant commands do not add paths.

Until a path set has its first result, file-dependent commands are disabled. An immediately opened first popup can therefore require reopening after the initial background result; there is no claim that an already displayed popup is dynamically repainted when work completes. Existing matching-path results remain advisory while a periodic refresh runs, including if a drive blocks. They can be stale. A changed path set cannot use the previous generation's results. The source keeps fresh synchronous filesystem validation at actual command invocation, followed by the existing operation-specific checks. This caching does not grant permission to recycle or open a file that later disappears or changes, and it does not eliminate operation-time races.

Stopping the worker marks shared state closed, drops pending/results and signals its condition variable. It never joins a blocked filesystem call on the window thread; in-flight work owns its state until it exits or the process ends. Worker/thread-creation exceptions disable advisory probing, leaving unknown file-dependent commands unavailable. Existing synchronous execution remains independent of the worker, but a disabled menu entry still requires the probing path to recover in a new window/process. Automatic worker restart after a fatal worker exception is not implemented here.

The current synchronous resolver remains available for invocation and existing callers. The new generic resolver applies the same command predicates with either cached or fresh regular-file answers. This is a responsiveness implementation based on UDM source inspection, not a newly measured or reverse-engineered IDM menu behavior. No runtime tests, benchmarks, fault injection, selection/menu/keyboard checks, cancellation/shutdown qualification, installers, installation or publication were performed. Full IDM parity remains incomplete.

All five production native targets built successfully with exit code 0 and report 1.42.0. The captured source hashes remained unchanged, and binary sizes/SHA-256 hashes are recorded. This establishes compilation and artifact identity, not responsiveness or runtime acceptance.
