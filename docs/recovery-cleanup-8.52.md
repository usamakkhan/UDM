# UDM 8.52: accepted recovery cleanup outside Model

UDM 8.52 detaches post-acceptance recovery cleanup from its own model lease. Both extension source manifests advance to 0.72.16; browser JavaScript is unchanged. Installed desktop remains 8.32 and installation stays deferred.

## Reproduced boundary

The [exact 8.51 control](../benchmarks/speed/recovery_cleanup_control.cpp) holds immediately before the actual owned journal-retirement call. Ordinary, replacement and original-scope recovery all deny independent model access while held, then reconcile exact bytes after release. [Control results and source/core hashes](validation/recovery-cleanup-8.52/cleanup-baseline-proof.json) and [instrumentation reconstruction](validation/recovery-cleanup-8.52/baseline-source-manifest.json). This proves lock ownership at the boundary, not disk syscall latency or an IDM speed gap.

## Accepted cleanup ownership

After snapshot-bound catalog proof accepts the recovery outcome, cleanup captures the current owned rows and descendant/scope inputs. It releases its own model lease while closing verified file handles, writing zone metadata, removing retained output and retiring the exact held journal. All operation jobs and target/staging/previous paths remain reserved. The immutable retained-output path is also reserved when it is a separate absolute path, before verification/cleanup begins; path syntax is captured without adding filesystem IO under Model.

Each cleanup checkpoint validates ownership, current membership, pointers, child graph and relevant accepted inputs before and after the observation. Private completed recovery additionally requires its exact receipt binding to remain present. Independent descriptions/settings and durable saves remain available and are preserved. A changed scope, catalog batch or successor receipt refuses stale continuation. Shutdown itself drains already-accepted cleanup; it still prevents a new recovery from starting.

Verified handles remain held through catalog acceptance. Their successful release now runs outside Model, and an exit guard closes still-held handles outside the same lease when verification or cleanup unwinds. Exact journal retirement is observed within RecoveryJournal immediately before disposition and after its successful close; the journal remains exclusively claimed until then. Private receipt erasure returns to Model only after successful cleanup and final revalidation, using the existing exact descriptor comparison.

## Failure means cleanup is pending, not completion rollback

The accepted catalog is already durable. No cleanup exception restores pre-publication counters/status or loses the accepted bytes. A failure before retirement retains its journal for explicit retry; a failure after retirement cannot recreate a consumed journal and instead preserves accepted history and any receipt for later reconciliation. Shutdown waits for all operation ownership and the discovery work token. Once catalog acceptance is proven, cleanup finishes through closing rather than abandoning its journal; pre-acceptance discovery and verification still refuse closing.

Actual read-only journals produce Windows error 5 during retirement in ordinary, private and paired recovery. They retain their exact intent and final file, then retire successfully after the fixture clears only its own read-only attribute and explicitly retries. A real retained-source reader refuses best-effort deletion without losing the accepted final file. A real hard-link retained alias can be removed while the final name and digest remain intact. Zone metadata and retained-source deletion keep their prior best-effort semantics; this increment does not claim their errors are newly reported.
