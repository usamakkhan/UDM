# Initial multi-Period live DASH selection

Build complete: all five native production targets and the UDM 1.0.4 / extension 0.63.63 installer compiled successfully. The unsigned candidate is staged, uninstalled and unpublished. Runtime behavior remains unverified; testing is deferred at user request.

Extension 0.63.63 can request an active Period for a live MPD that already contains multiple Periods. It no longer rejects such a catalog solely because of its Period count. The ordinary recorded catalog and existing single-Period live path remain unchanged.

The extension requires the native `live-dash-period-selection` capability and calls the read-only `dash-live-period` native-host action. This action does not create a download or bring the app forward. It fetches a fresh MPD, synchronizes through its declared UTC timing source, and resolves Period timing with the native parser. It selects the Period containing server time minus availability start and the declared suggested delay (six seconds when omitted). The entire clock-uncertainty interval must fit inside one nonempty Period. Ambiguous boundaries, expired manifests, gaps, missing stable IDs or unsupported timing produce a refresh error rather than a local-clock or first/last-Period guess.

The browser builds its quality and audio catalog from the matching stable Period ID in its fetched document. All Period IDs must be unique and stable. A native-resolved Period may have an inferred start; the browser does not invent one. If the native query's final manifest URL differs or its selected ID is absent from the browser document, the user is asked to refresh formats. Before handoff, the extension queries the active Period again and rejects a selection whose Period changed while the menu was open.

The query requires extension permission for the media origin. Captured GET headers are tied to the same tab, frame and document, with optional credentials governed by the existing cookie setting and permissions. Explicit cookies are read for the manifest URL's path. Native manifest redirects retain the existing cross-origin header stripping; implicit browser sessions, stored site logins and Windows intranet authentication are disabled. UTC timing requests use the existing anonymous clock-fetch path and configured transport/proxy preferences. Native query execution is bounded to 30 seconds, while the handoff retains its existing preparation deadline.

The selected plan retains a `livePeriodSelection` marker and the usual stable track IDs. Capture, later Period transitions, recovery and final joining use the native live session implementation. There is still a possible boundary change after the handoff check; capture must reject unavailable or changed tracks rather than claim a complete file. Live captions, SegmentList/SegmentBase and incomplete low-latency chunks remain unsupported. A Period removed before required media is captured can still prevent completion.

JavaScript syntax checks passed for the changed Chromium scripts, which are mirrored in Firefox. Runtime browser, server-clock boundary, recording and playback tests remain deferred at the user's request. Build/package evidence is in `validation/browser-live-dash-period-selection-build-20261028.json`. The new app and extension are staged, uninstalled and unpublished.
