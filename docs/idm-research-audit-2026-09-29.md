# IDM research compared with installed UDM — 29 September 2026

**UDM 0.73.0 / browser 0.47.0 still has confirmed missing workflows, partial implementations, and unverified behavior. The evidence does not support a 99% parity claim.** This audit reconciles the expanded research from “Reverse engineer IDM More” with current source and release evidence. It adds a reproduced Firefox build regression and makes the cancellation-dialog gap more precise.

Fresh verification: **53 deployment-receipt files and 74 browser files match their recorded SHA-256 hashes**; the current installer and installed IDM reference executable also match. Six source-execution cases reproduce the file-recognition limitation. Running the actual browser preparation script on a disposable copy reproduces a missing Firefox dependency. No personal downloads, installed application code, browser configuration, or driver settings were changed. The prior release's 1,938 passing checks were reviewed, not rerun.

[Machine-readable evidence](research-audit-2026-09-29/audit-evidence.json), [recognition observations](research-audit-2026-09-29/capture-recognition.json), [Firefox generation reproduction](research-audit-2026-09-29/firefox-generator.json), [fresh signatures](research-audit-2026-09-29/signatures.json).

**Concrete omissions and differences**

“Missing” means the inspected path has no complete workflow. “Partial” means relevant functionality exists with specific limits. “Unverified” means evidence is insufficient; it must not be treated as a demonstrated defect. Research architecture differences alone do not prove a speed or compatibility disadvantage.

**What the research itself still cannot answer**

The [expanded static report](idm-complete-static-analysis-2026-09-27.md) records 988 entries, 465 unique contents, 59 native binaries and 88,975 recovered pseudocode functions. There are still 38 decompilation failures and 1,801,253 executable-section bytes outside recognized functions; some residual bytes may be data or padding. These are research coverage counts, not counts of understood product behavior.

Full file-recognition rule semantics, native/driver capture-flag meanings, request layouts, indirect calls and some recovery behavior remain unresolved. Not every graphical resource was visually reviewed. Automatic decompilation has not recovered the original source tree. The research includes build 11, while the installed comparison binary is build 10; its matching hash was rechecked here. A build 11 branch must not be described as an observed build 10 behavior.

Some intermediate summaries are stale: `capture-config/summary.json` predates the fuller browser-flag explanation in `browser-rule-effects.json`. The latter and the final report clarify browser control flow; neither establishes all native/driver runtime effects. Older gap reports likewise describe 0.70/0.72, not current 0.73.

**Implementation order from this audit**

1. Incorporate the staged recognition and Firefox-generation fixes after rebasing host expectations to native 0.73; finish actual isolated Edge acceptance before deployment. Preserve the separate byte-signature limitation.
2. Implement R04 completely, including both exclusion scopes and the suppression/re-enable setting, with correct capture ownership and counter behavior.
3. Improve player association and capture rules with positive and negative real-site cases; finish unsupported browser request/proxy handoffs.
4. Define and qualify automatic driver-to-download handoff, then run controlled transport/recovery/speed tests.
5. Finish remaining integration/backup/Grabber work and the GUI, system-behavior and distribution qualification matrices.

This was an audit. It did not install the staged extension, claim a speed winner, rerun all prior tests, or establish complete parity. Reproduction and exact current source hashes are retained in the accompanying evidence directory.
