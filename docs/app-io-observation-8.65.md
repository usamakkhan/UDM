# Real MFC-app I/O observation, 8.65

This is diagnostic research against the existing 8.65 build, not a new product increment, installation or IDM comparison. The normal synchronous Transfer object is linked; the private ordered-body experiment remains disabled.

## Target and collection boundary

`benchmarks/speed/finish_app_observer_control.cpp` links the qualified App entry object, normal core and application resources. Its console entry calls the stock MFC `wWinMain` with a private catalog, unique instance tag, background mode and suppressed progress/completion UI. It reports QPC immediately before and after that entry. MFC entry return includes `Application::ExitInstance`; controller gates and later CRT/global teardown are excluded. Console startup and instrumentation also differ from the installed GUI executable. These results must not be presented as full process-lifetime or uninstrumented performance comparisons.

The existing `finish_user_io_agent.js` records owned-path Win32 and native file calls. `finish_app_io_read_addon.js` additionally records ReadFile calls for scoped known handles; it records counts, not file contents. Read hooks remain loaded through normal process exit. It does not observe every possible read mechanism or kernel scheduling. Native path resolution precedes each native begin timestamp and has observer overhead. The existing agent's `.bin` bodyCandidate hint is inapplicable to App `.data` storage: analysis selects the actual unique body path and verifies byte offsets instead.

The launcher uses ordinary user permissions. No administrator session, IDM attachment, installed binary replacement, personal catalog change or security-policy change was required. The host runtime printed `Unable to start idund: idund did not start listening` during observed runs. Attachment, scoped events and normal target exits succeeded; that does not prove the failing runtime component healthy.

## Integrity and interval validation

Six controls completed: 8 KiB C: without hooks, with existing hooks, and with read hooks; 64 MiB C: sequential, D: sequential and D: eight-connection split with read hooks. Every output matched its expected length and SHA-256, completed its catalog transaction, exited normally and passed a separate post-exit output flush. Payloads were deleted after verification.

The [sanitized results](validation/app-io-observation-8.65/results.json) are generated by `benchmarks/speed/summarize-app-io.py`. For all five observed runs it verifies no dropped events or remaining tracked file/mapping handles, successful nonpending body writes, exact contiguous byte-offset coverage without overlaps, and a unique same-thread/same-handle Win32 enclosing call for every native write/flush. Native intervals are nested inside Win32 intervals and must not be added to those envelopes. Private receipt hashes identify the analyzed inputs without publishing usernames, catalog contents or absolute local paths.

## Measured locations, not benchmark rankings

| 64 MiB case | Last native body-write completion to MFC return | Final native body flush |
| --- | ---: | ---: |
| C: sequential | 60.121 ms | 5.726 ms |
| D: sequential | 217.997 ms | 90.771 ms |
| D: split | 906.767 ms | 722.282 ms |

These are single instrumented samples, not medians. They use one QPC domain. Origin timestamps and the job's millisecond clock are not interchangeable with QPC; no unsupported clock conversion is used.

In the D: split sample the body flush starts 9.84 ms after the last native body write. The publication-journal flush starts at 754.10 ms and takes 74.17 ms; the final catalog flush starts at 832.45 ms and takes 35.77 ms. Three subsequent catalog reads take approximately 0.04–0.05 ms each. ReceiverThreadsSeconds includes live reception and cannot be treated as a post-download join delay. PrefinishFinishSeconds is 0.0003081 s in this sample.

This identifies a real final-body-flush interval as the dominant observed tail, rather than repeated catalog parsing or a slow body open. It does not distinguish disk queueing, filesystem/filter work and scheduling, nor show IDM's corresponding durability behavior. The earlier 8.65 text-cache improvement addresses a separate measurable catalog cost; it cannot remove this body flush.
