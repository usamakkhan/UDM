# Cancellation recovery — 8.39 / browser 0.72.3

Failed pending cancellations now remain in a bounded recovery queue rather than disappearing with a failure flag. The queue shares the existing 64-presentation bound. Failure handling transfers an existing map node without allocating another ownership entry, retains private error text up to 2,048 bytes, and signals the main window after releasing the state lock. The main timer supplies a fallback when a notification cannot be delivered or another modal defers presentation.

The shared native recovery dialog shows the file and actual failure detail, explains that cancellation could not be confirmed, and offers explicit background Retry or Close. Its independent capture owner keeps the main list in the background. Retry disables conflicting actions while persistence runs; the dialog's timer and painting remain responsive. A successful callback closes the recovery window. Another failure updates the notice and enables an explicit next attempt. Closing an idle failure notice acknowledges it without asserting that cancellation succeeded or changing the download's state; normal review of unresolved pending work may resume.

Each retry/dismiss action carries a failure generation. Duplicate or stale actions cannot target a newer attempt. The failure queue and an active cancellation retain the pending-offer claim, preventing a normal refresh from reopening File Info before recovery is handled. User-confirmed work remains protected by the existing cancellation rules. The queue does not silently retry failed writes.
