# UDM 8.44: retire the unproven overlap and retain recovery protection

Version 8.44 restores the ordinary download path to serial write-only body flush, durable intent, rename and catalog acceptance. The 8.43 body/intent overlap did not demonstrate a speedup in its two alternating D: trials, so its extra per-file task, writable preparation mode and handoff flag have been removed from production. No new ordinary intent carries `FlushBeforePublish`.

Recovery still understands the retired candidate's saved early intents. It verifies and forces their preserved bytes before acceptance, refuses denied write access and invalid flags, and keeps changed/truncated/foreign sources and journals intact. The final-name pin introduced during that work remains through ordinary catalog acceptance. A separate NTFS hard-link name can rename independently: the tests verify that final-name stability and byte-write exclusion remain intact instead of requiring all aliases to be immovable.

All 1,491 focused checks passed across ten suites: preparation 87, ownership 186, publication commit 347, publication recovery 73, completed checkpoint 145, replacement commit 395, synchronization replacement recovery 16, catalog checkpoint 40, catalog coordinator 46, and early-intent recovery/final-name protection 156. The legacy cases seed full Size/Received accounting to exercise the refusal to reuse unflushed completed-byte records. Five native products and ten fixtures are built as 8.44. Both extension source manifests are 0.72.8; browser JavaScript is unchanged. [Native qualification and exact hashes](validation/serial-publication-8.44.json).

One actual ordinary 64 MiB download on D: matched its independent byte count and SHA-256, used the restored write-only serial flush path, emitted no experimental overlap marker, consumed one origin request and exited normally after its application-owned work. The output was explicitly flushed after exit and removed. Its exit tail was 348.894 ms and its post-exit durability tail 374.636 ms. REA analysis ran concurrently, so this is a lifecycle/content smoke, **not a controlled timing comparison or evidence of a speedup**. The higher observed tail is retained; it must not be compared as a new benchmark against the earlier two-trial medians. [Complete smoke record](validation/serial-publication-8.44/serial-64m-smoke.json).

The rejected candidate is preserved as a small reverse-applicable [source delta](../benchmarks/speed/experiments/retire-overlap-8.43-to-8.44.patch). A temporary reconstruction verified all ten recorded 8.43 source hashes, then the temporary copies were individually removed. This proves source reconstruction, not byte-identical rebuilding of timestamped executables. Old binary hashes remain as evidence; their compiled artifacts are retired. [Archive verification](validation/serial-publication-8.44/experiment-archive-verification.json).

## What REA found in the installed IDM binary

The reviewed x86 executable has SHA-256 `03CC62E9ADB77A380F9DC12F67CCAAEE5106F12844AA73CE32C914DDD16D607C`. The known call flow is update routine `0x5bb350` → file-list flush `0x55ac20` → wrapper `0x570290` → `FlushFileBuffers`.

In that known path, explicit flushing is inside the zero-control-argument branch, after an elapsed-counter test greater than 40,000 ms, and when an effective byte-rate field is below 512,000 bytes/s (500 KiB/s). The effective rate includes an integer tenth increment and an optional cap; this threshold is not necessarily a direct comparison against raw throughput. Four reviewed socket-closing helpers and a destructor-like session routine pass control argument one and bypass this branch. Four receive-loop/update callers pass zero.

The unit verification combines REA's clock/helper analysis with bounded native disassembly and the image's double constant 1000.0. The clock resolves to `_ftime32_s`; Microsoft's [CRT documentation](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/ftime-s-ftime32-s-ftime64-s?view=msvc-170) identifies seconds and a millisecond fraction. The byte-count calculation multiplies by 1000, divides by elapsed milliseconds, then uses a floating-to-integer helper. The helper itself is not the rate formula. The bounded inspection used the existing MSVC toolchain and Microsoft's documented [DUMPBIN range option](https://learn.microsoft.com/en-us/cpp/build/reference/range?view=msvc-170). No proprietary pseudocode was copied into UDM. [Sanitized static facts and evidence hashes](validation/finishing-8.44/idm-flush-caller-audit.json).

These are static findings about one resolved call chain. They do not prove that IDM never flushes elsewhere, define its full crash-durability contract, or establish an exact timer cadence. The guard is progress-call driven, not a guaranteed every-40-seconds timer. No new UDM pacing threshold was implemented from these findings.

The next runtime gate is a fresh nonce-scoped IDM observation: a short fast case, a slow case crossing 40 seconds, and a longer case crossing 40 seconds above the effective-rate threshold. Record actual native flushes, final hashes, app process exit and a separate symmetric output flush; retain every loss and remove payloads. This remains pending because the existing IDM and old UDM 8.39 observation app are still open and desktop input again fails with `GetCursorPos: Access is denied`. No process was force-terminated. The recovery mutex reservation/caller migration and the original slower sequential/split cases remain unresolved.

## Runtime follow-up: slow download crossing the known guard

After the user cleared the earlier completion dialog, an owned 9 MiB sequential download at a 200,000-byte/s origin cap completed through the existing IDM instance. It used one request, delivered exactly 9,437,184 bytes, and matched the independent SHA-256. The native observer recorded one successful body-file flush, nested inside one Win32 flush (one operation, not two). Its Win32 call began 39.325 seconds after the first recorded body write; native flush time was 0.746 ms, with body writes continuing for another 6.561 seconds. This supports the conditional mid-transfer flush found statically. The elapsed counter begins before the first body write, so this is not an independent exact 40-second timer measurement.

All 828 observed body writes used implicit offsets. Their completed-byte total matches the output, but that alone does not establish interval coverage or complete observation. Unmatched paths and unresolved handles remain limitations. Existing-instance shutdown was not measured, and instrumentation prevents a speed comparison. No UDM flush policy or application code changed; native 8.44 and extension source 0.72.8 remain current. The payload was deleted after verification, and the observer detached normally. [Sanitized runtime evidence](validation/finishing-8.44/idm-slow9m-native-observation.json).

A new IDM completion dialog is visible. One normal-close input failed again with `GetCursorPos: Access is denied`; the user has been asked to close it before the remaining above-threshold runtime case. No app was terminated and no installation was attempted.
