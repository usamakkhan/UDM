# Legacy completed DASH recovery, UDM 1.40.0

The older resource store at git fd778b8 moved the completed payload to its .part name, then called atomicText to publish a protected full receipt. Its decoded receipt contained exactly binding, bytes and sha256. Core.cpp::atomicText wrote the .receipt.json.tmp scratch file and flushed it before replacing the primary receipt. A process interruption could therefore leave the promoted payload and valid protected receipt scratch without the new .commit.json marker introduced in 1.39.0.

Recovery now checks that known legacy scratch after attempting current completion intents. It requires the schema-1 protected envelope, an object with exactly those three full-receipt fields, the current media-binding digest, a positive bounded integer size and a SHA-256 value. Range/version callers retain their required byte counts. Only the already-promoted .part payload is considered for this path. The held file must have the exact size and hash; incomplete prefix metadata, arbitrary orphan bodies and unknown extended record shapes are not completion evidence. Legacy hexadecimal checksum casing is normalized.

Receipt publication itself rewrites the scratch path. Before doing that, recovery writes an independent protected completion intent with an explicit promoted-payload stage. A second interruption can then recover from that intent even if receipt-scratch rewriting was interrupted. The current intent reader accepts the promoted stage and avoids hashing the same destination twice. Existing temporary/prefix intents retain their prior handling, and normal full receipts retain their existing format.

The canonical intent must be successfully written before republishing. Inspection/hash failures leave the candidate unaccepted; publication errors propagate with completion evidence retained. Existing cancellation, regular-file/reparse checks, digest-derived path bounds, metadata protection, full-receipt publication and post-success staging cleanup remain in force. This extends the 1.39.0 recovery path through existing inspection/reconciliation rather than creating a separate import command or HTTP request.

The historical-source check used the local git blob for native/DashManifest.cpp at fd778b8eb7a37777b6ef7a459a4b18649a61b079 and the current atomicText implementation. It did not inspect or claim IDM's private recovery-file format. Older applications that do not understand the promoted pending stage can still ignore it/refetch; published full receipts remain compatible with their existing reader.

This does not recover legacy bodies that lack authenticated completion evidence, nor does it accept a prefix merely because its saved byte count reaches a declared total. Missing/invalid protection, wrong binding, extra fields, truncated/mismatched data and unsupported schema variants remain cache misses or storage errors under the existing policy. Power loss, repeated interruption, corruption, permissions, filesystem races, migration, reconciliation and playback remain unqualified. No runtime tests, installer creation, installation or publication were performed. Full IDM parity remains incomplete.

The production build finished with its final success message and no remaining build process. All five production executables report 1.40.0; their sizes and SHA-256 hashes are recorded, and the captured source hashes remained unchanged. The original build shell exit code was unavailable after context compaction; the receipt records that evidence limit. This establishes compilation and artifact identity, not runtime recovery behavior.
