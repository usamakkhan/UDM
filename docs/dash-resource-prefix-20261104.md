# Resumable DASH resource prefixes, UDM 1.38.0

The DASH resource store previously deleted its temporary response after an interruption and refetched the resource from zero. This also applied to the early streaming path added in 1.37.0. Whole resources without an existing range/version binding can now retain a verified prefix when the response has one accepted strong ETag. Shared ranged and version-bound resources retain their earlier contract.

DashResourceResume uses a .resume payload and protected .resume.json checkpoint keyed by the existing media binding digest. Metadata binds that digest, the canonical effective URL, strong ETag, received byte count, known full size or -1, and SHA-256 of the flushed prefix. The open payload handle rejects reparse points and disallows other writers/deletion while in use. The first write checkpoints, then new data checkpoints at most once per second; cancellation/failure also attempts a final checkpoint. Data is flushed before atomically publishing its protected metadata. In-flight hashing uses SHA-256 state duplication rather than rereading the file for every checkpoint; [Microsoft documents BCryptDuplicateHash's state-copy contract](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptduplicatehash).

On reuse the metadata is validated, the held file's size is checked, and exactly the checkpointed prefix is reread and hashed before any conditional request is offered. A longer file can contain an uncheckpointed crash tail. That tail is truncated only after accepting a matching resume response; it is not trusted as downloaded content. The prefix URL must match the current canonical request URL exactly. Rotated signed URLs do not inherit one another's validator merely because the media binding or ETag spelling is similar.

The client sends Range from the saved offset with the strong ETag in If-Range. Append requires HTTP 206 with one matching ETag, one exact Content-Range starting at that offset and ending at the fixed entity end, a bounded numeric total, and consistent length/coding metadata. Multipart and encoded variants cannot be appended. The prior known full size must agree when available. A 200 response is consumed as a full replacement. Invalid remaining-range responses and 412/416 results disable resume for that URL and retry it once as a full request, without consuming a redirect hop. Existing origin-scoped headers and HTTPS downgrade restrictions still apply. These choices follow [RFC 9110's If-Range and range-response semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5); they are not an observation of IDM's private resume algorithm.

Accepted append continues hashing from the verified prefix and counts only the new response body in the network callback. The existing maximum resource size, expected-size checks and early-response framing requirements still apply. Completion flushes the working file and compares its disk-read SHA-256 with the running prefix-plus-tail digest. Only then does the store promote it to the complete resource and publish the existing full receipt. Prefix state is removed afterward. A prefix checkpoint never marks a recording segment committed and is not independently fed to assembly or stop-and-save output.

Missing, weak or unsupported ETags use the prior temporary-file path. Prefixes with invalid metadata/hash are ignored; redirected recovery files remain errors under the existing storage policy. A full retry with a valid new entity tag replaces prior prefix state only after the response has been accepted. A completed prefix at the entity end can still require a full refetch after a 416. A crash in the narrow payload-promotion/full-receipt-publication gap can likewise require refetching; this increment does not claim elimination of every crash window.

This is byte-prefix recovery under a strong HTTP identity contract. It does not parse CMAF chunk boundaries, salvage an unfinished segment into final media, or resume validator-free/growing shared resources. Periodic flushing, prefix verification, running hashes and final disk verification add I/O/CPU work; throughput and cancellation latency have not been measured. The checkpoint interval is driven by data arrivals, not a separate timer. Filesystem/device flush behavior, hard crashes, metadata failure, changing validators, malformed ranges, transport resets, proxy/redirect cases, shutdown and user-visible progress all require runtime qualification.

No tests were run, and no installer, installation or publication was performed. Both browser sources remain unchanged at 0.63.85. Full low-latency and overall IDM parity are incomplete. See [source record](reference/dash-resource-prefix-20261104.json) and [build receipt](validation/dash-resource-prefix-build-20261104.json).

The production-only native build completed with exit code 0. UDM, NativeHost, Monitor, SetupHelper and Automation all report 1.38.0; their sizes and SHA-256 hashes are recorded. The recorded source hashes remained unchanged throughout the build. This verifies compilation and artifact versions, not runtime prefix recovery or performance.
