# File Info receipt joining — 8.35 / browser 0.71.99

## Problem and implementation

The 8.34 characterization reproduced a retained File Info dialog stuck as Uncertain when its explicit Retry raced a matching browser resubmission. There was no duplicate committed download, but the original presentation did not follow the competing owner's later outcome. [Preserved characterization](validation/finishing-8.34/pending-retry-race.json)

The admission registry now provides a read-only observation of one exact token and selection fingerprint. This observation owns neither a lease nor a snapshot ticket. Its condition-variable wait ends after live installation, or after the original owner and all captured publications become terminal. A published but uninstalled entry remains evidence of publication, never permission to resubmit. Owner release and installation notify observers; snapshot completion already did so.

Only File Info's joined background Retry worker opts into this wait. Ordinary browser submissions, legacy entry points and nested ordinary admission contexts keep the existing non-waiting busy contract. The worker releases the Manager mutex before waiting, then rechecks the durable receipt, fingerprint and live job under that mutex. A definite competing failure can yield to the already requested Retry after ownership retires. A release barrier, changed selection, removed accepted record or irreconcilable publication remains an error. This introduces no timed retry or transfer pacing change.

The existing inbox session carries cancellation and the dialog's local draft across the resulting identity. Cancelling the original generation while its worker is joining remains nonblocking for the dialog; the cancellation worker cleans up the accepted joined identity once it is available. A wait does not cancel another owner's persistence or bypass durability. Application shutdown stops browser integration before joining the retry worker; full session-end and crash acceptance remain separate gates.

## Qualification and limits

All 1,486 checks pass across thirteen focused backend fixtures and two rendered File Info runs (153 checks in each light/dark mode). The new race fixture passes 58 checks; registry ownership/observation passes 55. Nineteen native executables (five production and fourteen fixture targets) were built and their 8.35 resources/hashes verified against 495 frozen inputs and 42 core objects. Core, FileWorkflows, Bridge and CaptureAdmission rebuilt; 38 objects remained unchanged. This is selected qualification, not the entire repository test catalog. The initial light-mode run verified the held-join HWND, draft and hidden owner, then failed a new post-modal identity assertion. That assertion attempted to obtain the current child through a deliberately weak session reference after the dialog had released it. The corrected fixture stores the bound job ID while the dialog still owns the child. Only that fixture translation unit was rebuilt; product/core bytes were unchanged. The failed result is [preserved](validation/retry-join-8.35/initial-ui-assertion-failure.json).

Installation remains deferred; the installed desktop is 8.32. Both browser source manifests advance to 0.71.99 under the paired version policy; browser JavaScript is unchanged. Personal catalogs and installed executable hashes are unchanged. No installer, release or Git push is part of this increment. Five prior 8.34 production executables were moved into their qualification area, not copied. Their historical source/build record is marked superseded; it must not be treated as a current install manifest. Removed 567 generated fixture/compiler files (155,983,501 logical bytes) individually, preserving current binaries/core, canonical media tools and compact evidence. [Cleanup receipt](validation/retry-join-8.35/cleanup.json)

The controlled race fixture uses a real detached temporary-flush gate and an explicit join checkpoint. It checks both competing outcomes, unchanged ordinary-busy behavior, fingerprint mismatch, one accepted receipt/job, duplicate Retry refusal and original-generation cancellation. The UI fixture holds the same race while the actual dialog's timers dispatch, edits destination/description, and uses Download Later after binding. Light/dark checks and artifact hashes are recorded separately from installed-browser acceptance.

The competing request in these owned fixtures calls the actual Manager admission path but does **not** publish its own independent browser File Info notification. Two notified producers, presentation coalescing and cancellation during those competing notifications remain open integration work. These results cannot close that broader gate. Installed browser qualities/formats, full application/session-end behavior and the existing finishing-delay performance target also remain open. No new IDM timing comparison or successful kernel attribution is claimed.
