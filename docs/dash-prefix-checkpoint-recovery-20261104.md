# Interrupted DASH prefix checkpoint recovery — UDM 1.47.0

The prefix writer flushes the retained payload before atomicText writes and flushes a protected .resume.json.tmp file, then publishes .resume.json. A process interruption can leave a newer complete scratch checkpoint beside an older primary, or a scratch checkpoint without a primary. The prior reader required the primary and ignored scratch metadata, so those attested bytes could require refetching. This source finding is from UDM's writer/reader sequence, not IDM's private journal format.

The constructor now reads the two fixed metadata candidates independently. Both retain the schema, current media-binding digest, canonical HTTP URL, strong ETag/qualified date, bounded positive prefix length, consistent known total and SHA-256 checks. Invalid or unreadable metadata can be ignored independently; existing reparse rejection remains an error. The storage folder must be absolute. Candidates are ordered by prefix length, with scratch first for equal lengths, but bytes are not accepted on metadata alone.

For the exact current request URL, offer opens the payload with the existing held-file type and write-sharing restrictions. It validates actual size and rereads exactly each applicable candidate's prefix through the SHA-256 hasher, trying the greatest length first. A hash mismatch or a candidate longer than the available file can fall back to the other metadata record. If no candidate verifies, that URL is rejected for the current helper instance, preventing repeated bad-prefix scans during redirect loops. There are at most two candidate hash attempts; a fallback can therefore require up to two bounded prefix reads. Storage read failures remain cache misses; cancellation propagates. Performance has not been measured.

After one candidate verifies, that helper stays bound to its selected URL rather than switching validators across redirects. Other URLs can still use the existing full-response path. Scratch selection rereads its exact saved envelope, checks it has not changed, and promotes it to the primary name with MOVEFILE_REPLACE_EXISTING and MOVEFILE_WRITE_THROUGH before returning a resume offer. [Microsoft documents those move options and their access requirements](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw). Changed or unpublishable verified scratch metadata raises an error outside the cache-miss handler; a local publication failure cannot silently trigger prefix replacement. The surrounding store preserves prefix state and retains its existing alternative/error policy.

Promotion publishes only a locally verified prefix checkpoint. It does not establish that the remote representation is unchanged. Range/If-Range still use the selected saved offset and validator; append still requires the existing matching HTTP 206, exact Content-Range/total, length, encoding and framing rules. Uncheckpointed tail bytes remain untrusted and are trimmed only after accepting append. Final resource publication still requires complete-body/size and whole-file/running-hash checks. Neither a prefix nor a checkpoint reaching a declared total becomes a completed recording segment on that basis alone.

When a valid full response is accepted into retained-prefix storage, begin removes both old primary and scratch metadata before truncating/resetting the payload. This prevents a superseded scratch from being reconsidered after a new body is started. A response without a usable validator still follows the existing ordinary temporary-file path; old prefix state is not treated as current remote proof. The published checkpoint format remains schema 1, so older readers can use a recovered primary under their existing validator support. Completion-intent/full-receipt handling from 1.39/1.40 remains separate.

No network-byte callback is invoked while hashing retained bytes. Recovered traffic is not counted again, and saved recording coverage is not increased merely by recovering prefix metadata. Missing attestations, invalid hashes, rotated URLs, completed-prefix 416 cases and local storage errors can still require refetching or intervention. The write-through flag is not universal proof against power loss or filesystem/driver behavior. Existing path races and concurrent-writer limits remain unqualified; no private IDM recovery equivalence is claimed.

All five production native targets built successfully with exit code 0 and report 1.47.0. The captured source hashes remained unchanged; executable sizes and SHA-256 hashes are recorded. Compilation and artifact identity do not establish crash recovery or transport behavior at runtime.

Runtime/parser/network tests, crash injection, corruption, flush semantics, permissions, redirects, concurrency, cancellation latency, performance and playback remain unverified. Installer creation, installation and publication are deferred. Full IDM parity remains unfinished.
