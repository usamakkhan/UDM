## Persistence coordinator

Introduce a serial catalog commit coordinator that owns write ordering and completion notifications. Each request carries a sequence, detached snapshot, included admission reservations and completion state. Never take the manager lock while holding the write lock; publish results after releasing the writer's lock.

Prepare a new media admission as a detached draft rather than calling the current mutation-and-rollback path and then unlocking it. The draft contains the allocated job ID, validated media selection, route/session binding, intended category/queue/destination, protected durable metadata and receipt fingerprint. Validation and reservation happen under a short manager lock; filesystem work and persistence happen outside it. Do not clone a Manager with its worker and recovery resources.

Reserve token and destination against both registered jobs and other pending admissions. The normal Manager snapshot used by history/export stays committed-only. A private persistence snapshot builder merges eligible reservations so a concurrent explicit or automatic write cannot silently omit a pending receipt/job.

This merge is a correctness requirement, not an optimization. If another newer snapshot containing the reservation succeeds first, it establishes acceptance. A failure in the originally queued admission write must not roll that success back. Track the reservation's included sequences and durable generation; notify acceptance from the first successful snapshot containing the exact ID/fingerprint pair.

On acceptance, install the job and receipt into the live Manager state and remove the reservation in one manager-lock transaction. Until that transaction finishes, persistence snapshots must continue to include the reservation. There must be no interval where neither live state nor overlay contains the job.

If admission fails and no successful snapshot contains it, release its reservation and retain the existing prior catalog. Remove only its owned temporary paths after all associated work is terminal. Ordinary catalog operations that cannot yet participate safely in this scheme—restore, repair, replacement journals and shutdown—need explicit barriers; do not let them bypass reservations.

Existing forced-save callers often hold outer manager locks. Audit them before claiming general nonblocking persistence. The first integration must remove the outer-lock I/O dependency for media admission; coordinator introduction alone does not do that automatically.

## Decision state machine

| State | Allowed work | Transition |
| --- | --- | --- |
| Validating | Validate selection, route, token and target reservation; no normal transfer | Prepared or rejected |
| Prepared | Publish immutable view; accept local edits and decision intent | Persisting |
| Persisting | Write immutable catalog candidate; UI remains responsive | Accepted, or failed only after ruling out a successful containing commit |
| Accepted | Install live job/receipt exactly once; bind existing dialog; admit prefetch | Reviewing, applying a queued decision, or cancelling |
| Reviewing | Existing committed File Info behavior | Start, Later or Cancel |
| Applying decision | Revalidate destination/category/queue and persist decision on worker | Transfer/queue, return to review on a recoverable conflict, or failure |
| Cancelling | Resolve any in-flight acceptance, persist the final release/cancel outcome, stop owned work | Closed with no unexpected transfer |
| Failed | Retain user draft and specific error; offer explicit recovery | Retry only when token outcome is known, or close |
