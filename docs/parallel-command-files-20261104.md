# Parallel advisory command-file checks — UDM 1.49.0

Inspection of the 1.42 implementation found that one blocked filesystem probe prevented its single worker from checking every subsequent path or selection. Closing remained nonjoining, but a disconnected drive could leave unrelated ZIP/Recycle commands without advisory answers. This is evidence from UDM source, not a new observation of IDM's private worker implementation.

AsyncFileStatus now lazily launches at most four shared-state workers per instance. Workers claim individual indexes from one sorted, deduplicated current request. Each filesystem call runs outside the request mutex. A changed path set replaces the current request; free workers take its paths, and results from stale requests are ignored. No unbounded queue or per-path thread is created. A blocked call can retain an obsolete request and its owned path/result storage until it returns; at most four probes can be outstanding.

Each completed current path updates a protected result map and revision. observe publishes an immutable map snapshot when that revision changes, so a completed answer no longer waits for every other path. Already returned snapshots remain immutable. A command requiring several files still needs positive answers for all of them. Unknown and inaccessible paths remain unavailable, and an already-open popup is not automatically repainted. Selection generation changes discard prior answers; same-path refresh retains its existing advisory answers.

The same request refreshes at most once per second after all its paths finish. It reuses matching result storage, and unchanged answers do not invalidate the published snapshot. Snapshot map copying now occurs on observation when answers change, under the short shared-state lock; very large selections can still add UI CPU work. There is no claim that all command processing is nonblocking.

Workers retain only shared request/cancellation state, never a Manager, job, HWND or owning AsyncFileStatus pointer. Stop marks closing, drops current state and wakes all workers without joining filesystem calls. Those calls finish independently or end with the process. The implementation does not forcibly cancel an operating-system probe. Four blocked calls can still exhaust the pool, including calls left by rapid selection changes; this is bounded concurrency, not per-volume isolation or a universal timeout.

A thread-launch failure leaves any successfully launched workers available; if none start, advisory probing is disabled. An unexpected worker exception disables the shared pool and wakes idle workers, preserving the previous conservative unavailable-command policy. Automatic replacement of blocked or fatally failed workers is deliberately absent, preventing unbounded threads. Actual command execution retains existing fresh validation and operation-specific checks; cached answers never establish authority to modify files.

All five production native targets built successfully with exit code 0 and report 1.49.0. Captured source hashes remained unchanged; executable sizes and SHA-256 hashes are recorded in the build receipt. Compilation does not establish runtime behavior. Browser source remains 0.63.85. Runtime tests, timing comparisons, pool saturation, selection changes, filesystem faults, shutdown and IDM interaction remain unverified. Installer creation, installation and publication are deferred. Full IDM parity remains unfinished.
