# Find site matching, UDM 1.34.0

The retained reference analysis identifies Find Next at 0x0047c2a0, the record matcher at 0x0045fd40 and its address helper at 0x0045ac70. The reference and installed IDM executables were read again; both report 6.43.10.2 and SHA-256 03CC62E9ADB77A380F9DC12F67CCAAEE5106F12844AA73CE32C914DDD16D607C, matching the retained analysis specimen. This turn inspected the existing Ghidra output; it did not run a fresh REA session or operate IDM.

The address helper first compares the complete UTF-16 address when whole-string mode is selected. If that fails, it finds ://, copies the following portion, truncates at the first slash and compares that entire portion. Instructions at 0x0045ad63 through 0x0045adb1 implement the delimiter/copy/truncation path; equality reaches the explicit true result at 0x0045ae1d. Failure reaches the zero result at 0x0045ae63. The decompiler's inferred void signature is therefore not taken as evidence of the return contract. Substring mode uses _wcsstr instead. The helper uses CharUpperBuffW when matching case-insensitively; the filename/description paths call the uppercase helper at 0x004543e0.

UDM previously used lowercase folding and only full-address whole-string comparison. It now uses Windows uppercase folding and the full-address-or-site rule. For a stored https://video.example/track, a whole-string query video.example can match the site; video remains a fragment and does not match in whole-string mode. Filename and description still require their complete value in whole-string mode. Match Case bypasses folding. This is the same Windows API family observed in the reference, not a claim of full linguistic equivalence; [Microsoft documents CharUpperBuffW's conversion and language limitations](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-charupperbuffw).

The site comparison is deliberately the literal post-scheme portion up to slash, rather than a normalized DNS hostname. Credentials and ports remain part of it. Query/fragment spelling and malformed/legacy-address behavior are not newly normalized. UDM applies this rule to its existing address scope, including exposed captured media endpoints. Exact mapping of every UDM media format to IDM's internal record fields is unverified.

DownloadSearch prepares the query once per Find Next call. For each candidate in the current visible order, the manager lock protects only a scope-specific owned copy: selected filename/description fields, or address inputs including protected headers/media plans and URL-only Video/Audio child records. Decryption, media-plan parsing, recovery-page resolution, Unicode conversion and matching occur after release. Only one row's copied protected plan is retained at a time, rather than copying every plan in the catalog. The copy itself and lock acquisition remain synchronous; the UI still performs matching, so responsiveness gains require measurement.

The compatibility matchesDownload helper delegates to the prepared matcher. Existing field, case, wrap and filtered-list policies remain. The reference Find Next has a stored cursor with reset/update paths; this increment does not claim to reproduce all those cursor rules, and retains UDM's selection-based start behavior. Each row is captured separately, so the search is not a transactionally consistent catalog-wide snapshot. Background metadata changes can be observed between candidates.

The existing FindAddressTests source now expects whole-site success and retains a negative fragment check, with parent-page case, literal authority and Greek sigma folding assertions. Those tests have not been compiled or run. Runtime tests, installed GUI/Unicode/performance comparison, installer creation, installation and publication remain deferred. Full IDM parity is incomplete. See [static evidence](reference/idm-find-site-20261104.json) and [build receipt](validation/idm-find-site-build-20261104.json).

The production-only native build completed with exit code 0. UDM, NativeHost, Monitor, SetupHelper and Automation all report 1.34.0. Their sizes and SHA-256 hashes are recorded in the receipt, and the recorded source hashes remained unchanged throughout the build. This establishes compilation and artifact versions, not runtime acceptance or measured search performance.
