# Browser presentation acknowledgement — UDM 8.85

UDM 8.85 / extension manifests 0.72.49 moves Main's post-dialog browser acknowledgement off the UI thread. Both the prepared-media handler and the ordinary browser-presentation route enqueue displayed receipt tokens on one owned worker. Returning from File Info no longer waits on that acknowledgement's Manager lock or save. This does not claim the initial dialog or every other UI operation is already free of synchronous work.

## Ownership and recovery

The queue accepts at most 64 outstanding entries, coalesces already-claimed tokens and copies only the fresh token list. A grouped presentation is suppressed only when **all** its tokens are owned; an older queued or failed acknowledgement cannot hide a fresh token in the same group. Successful callbacks retire claims after Manager returns. A failed save retains its claim and exposes a bounded error with a stable request/attempt identity.

The browser-owned recovery dialog offers asynchronous Retry and Close. Retry operates on the exact failed attempt; stale buttons cannot consume a newer failure. Close retains the unresolved claim for this session without pretending it was durably saved, allowing the persisted offer to be recovered on a later launch. Fresh mixed-group tokens remain eligible. There is no automatic retry loop. Normal shutdown drains accepted work and joins the worker before Manager shutdown/destruction; a failed owner shutdown can restart the joined queue. Result-only weak notifications use the existing window identity checks. Recovery excludes conflicting prepared notifications and browser refreshes while its notice is open.

The queue acknowledges its captured tokens only. Existing Start/Later/pause transitions can independently retire job presentation markers as part of the decision save; this increment preserves those transitions. In that common case the later acknowledgement is idempotent, but obtaining Manager on the UI thread could still have stalled the return path.
