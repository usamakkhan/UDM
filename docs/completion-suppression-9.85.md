# UDM 9.85: save completion preferences without freezing the dialog

UDM 9.85 moves the completion dialog's suppression-preference save off the UI thread. Five native programs build as **9.85** and both extension source manifests advance to **0.73.49**; browser JavaScript is unchanged. The candidate is **uninstalled**. Full IDM visual and performance parity remains open.

## Measured cause and change

The 9.84 checkbox handler called `preferences()` and then `manager.setSettings()` synchronously. In a frozen owned dialog, another thread held the catalog until its 500 ms watchdog expired. Clicking “Don't show this dialog again” blocked the UI for **563 ms**, then persisted the setting normally. This measures a checkbox handler, not download finishing or dialog first paint. [Frozen result](validation/completion-suppression-9.85/baseline/results.json).

[CompletionSettingsTask.hpp](../native/CompletionSettingsTask.hpp) now owns an accepted save on a joined worker. It reserves the existing decision guard before returning to the UI, reads current settings under the model lock, and merges only `SuppressCompletionDialog`. A value already saved does not cause another catalog write. Worker inputs are values and a weak wake-up callback; no window or control enters the worker.

[App.cpp](../native/App.cpp) disables duplicate checkbox input while that save is pending. Close stays usable and may destroy the originating dialog; the accepted task remains owned by the main window. Acknowledgement synchronizes a surviving checkbox with the committed value and updates other open completion windows. Failure restores the committed value and reports the error on the surviving dialog or main window. Main-window shutdown defers while a save is accepted, so shutdown cannot silently abandon it. The existing completion file-action queue remains intact. [Isolated implementation, registry and maintained-test delta](validation/completion-suppression-9.85/completion-suppression.patch).

[Backend results](validation/completion-suppression-9.85/build/suite-results.json).

The checkbox handlers return in **0–16 ms** while the catalog writer remains held and before its watchdog expires. Close and the main timer remain responsive, and the accepted setting persists after the source dialog closes and through catalog reopen. Unchecking in a later explicit dialog restores automatic completion and reenables input. Zero is a coarse-clock observation, not a zero-latency guarantee. [Current dialog checks and timings](validation/completion-suppression-9.85/ui/suppression-results.json).

The existing **42 contention/file-action checks** and **274 retained-reference dialog checks** pass again, for **340 current UI assertions**. The reference fixture now waits for the real accepted save result before asserting persistence or dismissing the real failure warning. No success is inferred merely from a pending checkbox. [File-action result](validation/completion-suppression-9.85/ui/contention-results.json), [reference result](validation/completion-suppression-9.85/ui/reference-results.json).

## Remaining gates

The initial completion snapshot still takes the model lock; icon/filesystem/shell operations may also take time. This fixes checkbox persistence responsiveness, not every completion delay. The prior IDM process was unresponsive to supported desktop input, so no new paired IDM timing, browser acceptance or installed acceptance is claimed. Previous slower sequential/split results remain open, including full process shutdown and final background work. Non-aligned live DASH ends also remain open. No installer, installation, administrator prompt, commit, push or release occurs in this increment.
