# Same-volume Move/Rename verification — 1.9.2

The 1.9.1 integrity correction introduced complete source/destination reads even for a rename on the same volume. UDM now uses a same-volume file-object fast path: it holds a read handle that denies data writes while allowing rename, records the volume serial and 128-bit file ID together with size, creation time and last-write time, then checks the destination against that identity. Ordinary and case-only renames no longer need to hash the entire file when this path is available. The same evidence is used to verify rollback and interruption recovery.

The destination directory is opened to determine its actual volume, including paths through junctions. Missing or unsupported IDs, reparse-point source files, and different volumes fall back to fresh SHA-256 verification. Old hash-based journals remain readable. Recovery using file identity is an object/metadata check, not cryptographic content verification after a crash. It does not claim to detect deliberate metadata-preserving changes. During the live fast path, the source handle excludes ordinary concurrent writers.

Microsoft documents the combined volume serial and file ID as file identity in [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info). The read-handle sharing behavior follows [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew). These are implementation references, not evidence of IDM's internal implementation. No third-party code was copied.
