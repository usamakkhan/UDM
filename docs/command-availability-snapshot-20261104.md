# Batched command availability, UDM 1.32.0

The main refresh previously called commandEnabled separately for each toolbar command. Each call locked Manager::mutex before asking the list control for selected rows, including commands that were always enabled. Stop/Cleanup/Recovery checks could scan the catalog repeatedly, and Stop All with progress windows used nested progress-window/job searches. The download context menu also held an outer manager lock across all menu creation, per-command checks and file probes. Merely changing the inner helper would not release that outer scope.

Toolbar creation and periodic refresh now call one updateToolbarCommands batch. Context-menu construction captures selection once and requests its command decisions together. Selection enumeration and open-progress-window discovery happen before the protected capture. Under the manager lock, ordinary eligibility predicates inspect current job state, active transfers and queue policy; requested global decisions share a catalog pass that stops once the requested positive/negative outcomes are known. Progress IDs are read under the lock from the already identified windows, without control messages. Menu Add/Move wording uses the same metadata scope as availability decisions.

CommandAvailability carries owned target paths and an optional FTP URL out of the protected scope. ZIP extension/presence checks, recycle regular-file checks and redownload FTP URL parsing resolve afterward, before toolbar/menu control updates. Exact-path file-status results are reused only within that batch, including shared ZIP/recycle paths. Missing/inaccessible files or resolver errors disable the relevant command instead of allowing filesystem exceptions to escape from that resolver. Existing completed/inactive, membership and synchronization-queue rules remain. The refresh-address predicate still delegates to Manager::canRefreshAddress, including its existing protected adaptive-plan checks; this is not a claim that every expensive predicate or other UI lock has been removed.

The context menu's outer lock was removed and replaced by the bounded capture. Move-destination menu helpers retain their existing scoped metadata reads before Windows menu calls. MFC command updates now obtain settings only for the tray/limiter/basket/theme/category indicators that need them. Plain commands skip settings copies. Unconditional enable checks avoid selection and manager access entirely, while selection-count-only commands use the control state without a manager lock. Selection enumeration returns empty if the list has no window, covering construction/destruction boundaries.

Availability results are not persisted or cached across user actions. commandEnabled performs a fresh query for execution as well as UI updates; the batch file cache has only call-local lifetime. This remains advisory UI state and does not replace operation-specific validation or eliminate file-change races between availability and execution. File probes still run synchronously on the UI thread and can delay a menu on slow storage; the improvement is that this routine's manager lock is released for that phase. No measured latency improvement is claimed.

Microsoft documents [MFC command updates](https://learn.microsoft.com/en-us/cpp/mfc/reference/ccmdui-class?view=msvc-170) and [the error-code filesystem query overload](https://learn.microsoft.com/en-us/cpp/standard-library/filesystem-functions?view=msvc-170). See [source-inspection record](reference/command-availability-snapshot-20261104.json) and [build receipt](validation/command-availability-snapshot-build-20261104.json). Runtime tests, performance/concurrency checks, live IDM comparisons, installer creation, installation and publication remain deferred. Full parity is incomplete.

The production-only native build finished with exit code 0. UDM, NativeHost, Monitor, SetupHelper and Automation all report 1.32.0; their sizes and SHA-256 hashes are recorded in the receipt. The recorded source hashes remained unchanged through the build. This is compilation and artifact verification, not runtime acceptance or measured responsiveness evidence.
