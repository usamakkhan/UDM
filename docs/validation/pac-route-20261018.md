# Browser PAC route comparison — 2026-10-18

Status: mismatch reproduced in isolated Chrome and Edge profiles. Browser PAC
capture remains unfinished. No production proxy behavior was changed.

The same PAC script returns proxy A, then B. A starts offline, so the browser
uses B. After A recovers, the browser still uses B. UDM's native transport,
given that identical script and target URL, uses A. Both responses are actual
HTTP bodies from the corresponding loopback proxies, rather than inferred
configuration values. Both browser runs passed these assertions.

This agrees with Chromium's documented failed-proxy cache, which can reorder
the PAC result. Script configuration is therefore insufficient evidence of
the route selected for an observed request. See
[Chromium proxy documentation](https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/proxy.md).

## Reproduction

Build `Udm.TransportPoolProbe.exe` using `native/build.ps1
-TransportPoolTestsOnly` (with the normal configured toolchain). With Playwright
available to Node, run:

```powershell
node tests/pac-route.edge-native-live.cjs <fresh-output-directory> <absolute-probe-path>
# Repeat with Chrome:
$env:UDM_TEST_BROWSER = 'chrome'
node tests/pac-route.edge-native-live.cjs <another-fresh-output-directory> <absolute-probe-path>
```

The fixture creates its own unpacked extension, browser profile, PAC server,
and two loopback proxies. It never modifies the user's profile or system proxy
settings. The destination uses `.invalid`; proxy responses contain only A or B.
It closes the owned browser and servers on completion, retaining evidence in
the requested output directory. `results.json` contains the route comparison;
raw native output and the temporary profile remain local.

The native probe used in this run was compiled against the current cached
backend objects, including the rebuilt transfer object. This was not a clean
full-project build. Its SHA256 was
`FA1F9096450A22951781DC6ABB859462A91396EA4BE9C5C5B405E78CC91BBFD0`.

## Implementation consequence

Do not label a freshly evaluated PAC result as the browser's captured route.
For exact browser route preservation, implementation would need request-specific
route evidence or a browser-owned transfer path. This is not yet established
as IDM's actual Chromium implementation. The follow-up
[reference configuration probe](idm-proxy-config-20261018.md) shows that IDM's
Chromium callback serializes PAC configuration for its desktop rather than
a resolved endpoint. UDM should distinguish configuration inheritance from
observed endpoint inheritance, and validate against IDM before treating exact
Chrome fallback-cache replication as a parity requirement. A separate
user-configured desktop PAC mode already exists. Firefox's request-specific
proxy metadata is a separate supported path and was not exercised here.

This fixture does not establish IDM's behavior, WPAD discovery, authenticated
proxy behavior, HTTPS PAC URL sanitization, or general browser parity.
