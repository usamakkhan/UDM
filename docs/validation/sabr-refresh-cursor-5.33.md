# YouTube recovery at a verified playback position

The isolated browser recovery fixture starts with one held 1080p job and a hash-verified copy of its media cache. It uses the real extension, native messaging host and desktop catalog code to admit a replacement, then makes a separate Save and Resume decision in the test driver. The original seed, installed app and personal browser profile are outside the fixture.

## Observed behavior in 5.32

| Replacement playback | Retained bytes before | Retained bytes after | Verified timeline after |
| --- | ---: | ---: | ---: |
| Opened at the beginning | 10,712,377 | 10,712,377 | 65.234 s |
| Opened near the retained cursor | 10,712,377 | 22,025,832 | 127.200 s |

Both matching offers were admitted to the original job. The first replacement used a newer request body and endpoint with the same video and audio revisions and duration. It was rejected on the first resumed request. A second playback opening in that run timed out. A separate experiment that tried to seek after page load timed out before it could capture a replacement. Opening a fresh tab directly at 65 seconds supplied a matching replacement and four native requests before the next rejection. The resulting cache contained 41 verified pieces, including all 23 original pieces with their original hashes.

These fresh profiles captured different sessions. The results establish a successful extension of the public checkpoint with the time-linked recovery page. They leave the reason for the later rejection open. Neither run completed a final file.

## 5.33 behavior

The desktop generates a time-linked YouTube recovery page for an attestation-held job with a single zero-based window and a consistent verified playback position. It rounds down to the whole second and preserves the original selection marker. Other recovery paths keep their existing address and behavior. The browser recovery fixture can follow the desktop-generated page directly.

Build the native driver with `-BackendTestsOnly -BackendTestNames StreamingContinuationTests`. Set `UDM_TEST_PROJECT` and `UDM_APP_EXE` to the staged browser tree and app. Set `UDM_STREAM_RECOVERY_DRIVER` to the matching test executable and `UDM_STREAM_RECOVERY_SEED` to a completed isolated run with a held, verified 1080p cache. `UDM_STREAM_RECOVERY_SEEK=1` follows the desktop-generated position, and `UDM_STREAM_RECOVERY_ATTEMPTS` sets the bounded number of replacement sessions. Run `node tests/youtube-handoff.browser.cjs <fresh-output> msedge recover warm`. The fixture verifies the original job ID, a pending replacement offer, and the bytes reused before reporting any new coverage.

## 5.33 qualification

The native streaming suite passed 242 checks, including a verified contiguous checkpoint, parallel coverage, inconsistent coverage and an ordinary refresh. The staged Chromium and Firefox 0.68.97 bundles each passed 19 streaming capture and 31 audio checks. All five native executables, 82 recorded inputs and 95 staged browser files matched their hashes. The successful recovery used isolated native and browser components with a test-controlled Save and Resume decision. Installed UI and full public completion need separate evidence.
