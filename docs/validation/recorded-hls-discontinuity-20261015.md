# Recorded HLS discontinuity support

Completed transport-stream HLS playlists can now cross an `EXT-X-DISCONTINUITY` timestamp boundary. The Chromium and Firefox parsers carry segment durations and boundary markers into the native handoff. The native recorded-download path writes a local HLS playlist referencing verified downloaded parts, then lets FFmpeg remux it. This preserves the boundary that binary concatenation would lose. The browser requires the native `hls-recorded-discontinuity` capability before handoff, so an older desktop app cannot silently ignore the marker. The tag's timestamp-sequence role is described in [RFC 8216](https://datatracker.ietf.org/doc/html/rfc8216).

Validation on 2026-10-15: all **60 browser test scripts** passed after the capability gate; the focused HLS catalog integration has **43** checks, including both browser handoffs and rejection with an older host; the final newly compiled native suite passed **2,632 checks, 0 failed**. A local HTTP fixture served the same MPEG-TS segment twice across a discontinuity. UDM downloaded two segments, produced at least four seconds of output, and FFmpeg decoded the finished file without an error. The complete native app/host/monitor/test build succeeded after the capability was added. The built native host passed **9** framed-protocol checks, including a real `hello` response advertising the new capability.

Recorded fMP4 playlists with an initialization map and discontinuity remain explicitly unsupported. The test uses a local fixture; it does not establish public-CDN or installed-app acceptance.
