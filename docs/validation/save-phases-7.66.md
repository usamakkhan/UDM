# Durable catalog I/O findings for 7.66

The production save path remains unchanged. The diagnostic build splits normal file writing and flushing only to timestamp the existing calls; it performs the same one WriteFile and one FlushFileBuffers operation. Its normal Core projection restores exactly to the recorded production source hash. All five product executables and 42 shared objects remain unchanged.

Four fresh browser/native runs measured flushing at 59.23, 14.50, 29.61 and 133.77 ms. Three write-mutex waits were below 0.001 ms and one was 52.04 ms. Snapshot and JSON work were small on these private one-job catalogs; larger histories remain unmeasured. The earlier 627 ms aggregate save spike was not reproduced, and these samples cannot establish its syscall owner retrospectively. The selected file fully decoded and matched the exact size and checksum shown before Start in every qualified run. See [raw measurements](save-phases-7.66.json).

Microsoft documents that frequent FlushFileBuffers calls can incur caching penalties and discusses unbuffered/write-through I/O as an alternative. That is a direction to evaluate, not proof that changing flags improves this workload. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)

Windows normally caches writes; its documentation describes the balance between flushing cost and losing buffered writes on system failure. Removing the current durability barrier would change acceptance/recovery behavior. Retain durable receipt/job admission while evaluating alternatives. [File caching](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching)

The next implementation should first identify overlapping automatic checkpoint work, then evaluate a measured durable-write change. If disk latency remains the dominant cost, separate provisional File Info presentation from durable admission using a private immutable offer and explicit pending, failed and committed states. Cover Start/Cancel races, write failure, lost acknowledgement, process termination, restart, exactly-once receipt recovery and prefetch ownership before shipping that architecture. Do not expose mutable uncommitted catalog objects or claim acceptance before persistence.

One preliminary observer run failed with PermissionError reading a catalog during atomic replacement. The observer retries only PermissionError/FileNotFoundError within its original 65-second deadline. Malformed JSON and state invariants remain fatal. Its first actionable timestamp is retained across retries. The four qualified replacement runs used zero retries; the transient branch itself is not live-verified. The initial successful cold run and failed warm run are retained outside the four-run timing comparison.
