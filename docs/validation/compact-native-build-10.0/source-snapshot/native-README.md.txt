# Building the native desktop

## Compact intermediate objects

Available in the 10.0 development candidate. [Validation scope and retained measurements](../docs/compact-native-build-10.0.md).

For development builds without debug symbols, add `-CompactIntermediateObjects -OmitDebugSymbols` to the usual build command. For example:

```powershell
./native/build.ps1 -ProductionOnly -OmitDebugSymbols -CompactIntermediateObjects -OutputRoot D:\UDM-Build
```

This reuses one `target-scratch.obj` for sequential top-level target compilations. Finished executables, shared core objects, generated automation files and diagnostic core variants remain separate. It does not remove earlier builds or change the existing media-helper copy policy. Debug builds and core-only builds reject this option before creating their output directories. Ordinary builds retain their existing object layout and do not generate compact metadata.

An exclusive `compact-target.lock` prevents two compact builds from sharing that output root. The build releases it on success and failure. Avoid concurrent ordinary and compact builds against the same shared core cache, as with other builds of that cache.

The output directory's `target-objects.json` records each successful target's object size and digest before the scratch file is reused, and its executable digest. Earlier object records describe consumed link inputs; only the last scratch object remains. The record starts incomplete and becomes successful only after every selected target links. This flag covers target compilation/linking, not tests, asset packaging, installation or release. Hashing uses .NET directly and does not require the `Get-FileHash` cmdlet.

Command-line downloads accept `/d URL`, `/p folder`, `/f filename`, and `/n` (silent). Use `/a` (or `--paused`) to add the download to Main queue without starting it. ## Find dialog regression

The backend targets `FindAddressTests` and `FindFilterCacheTests` cover Windows reference folding, address matching, query-scoped immutable snapshots, positive/negative cache hits, changed metadata and eviction. Both accept a fresh absolute results directory and write `results.json`; `FindAddressTests` also retains its older explicit JSON-file argument. Build them with `native/build.ps1 -BackendTestsOnly -BackendTestNames @('FindAddressTests','FindFilterCacheTests') -OutputRoot <absolute build root>`. Cache timing is a synthetic snapshot comparison, not full-window or IDM timing. [Byte-matched reference search path](../docs/reference/find-windows-fold-7.50.json).

The Find dialog component fixture compares the 7.52 cached Find Next handler replay with the actual current handler in the same owned window. It alternates seven trials of eight calls for filtered/unfiltered protected captures and filenames, plus a valid 2,047-unit Unicode description query. Both share the current list-refresh/backend code; this is not an older-executable or IDM comparison and has no timing pass threshold. It verifies disabled-field return, selection/wrap preservation, query transitions and matching after hiding the filter. [Reference no-fields guard](../docs/reference/find-next-7.51.json).

Hot Find Next lookups borrow the canonical UI query while doing only memory comparisons. Before a miss can decrypt/parse data, the handler takes an immutable witness outside the manager lock. Partial queries still normalize as needed. It rechecks query identity for each candidate, retains the candidate across matching, and abandons an outdated scan if the query or visible candidate changes. These ownership checks do not establish a forced Windows-message reentrancy replay; keep that acceptance scope distinct from ordinary source/query invalidation tests.

The query-bound cache remains usable while filtering is hidden. Visible category/queue candidates mark membership without promoting unused entries; a refresh discards entries outside that cohort. Actual cache hits and completed matching update the LRU order. Retention is capped at 8,192 entries and a 32 MiB logical cost counting JSON values, object keys and string payloads. This is a snapshot budget, not an application RSS limit. Oversized snapshots still produce matching results without retention. Expected-query guards prevent stale-query reuse/publication; changed sources are compared under the job lock before reuse, while decryption, eviction and snapshot destruction remain outside it. The fixtures cover entry/byte eviction, disabled retention, cohort removal, hidden-search source/query changes and both filtered/unfiltered handler comparisons.

Progress snapshot regression: build the `ProgressRecordViewTests` backend target and run `Udm.ProgressRecordViewTests.exe <fresh absolute results directory>`. It checks immutable display projections, form receipt state and visible/hidden range policy. It also checks ordinary, split, playlist and SABR address projection and cache invalidation. The address benchmark compares copying/comparing an unchanged six-MiB synthetic plan with borrowing its fields for comparison; both still read the selected bytes. Its synthetic timings are diagnostic, not whole-app or IDM performance claims. Pair it with `native/test-progress-dialog.ps1 -BuildRoot <absolute build root> -RunRoot <fresh absolute results directory>` for actual component controls and timer handling. Use `-SkipBuild` only with a fixture rebuilt from the intended source. Qualification: [7.49 address refresh and unresolved search expectation](../docs/validation/progress-address-7.49.json), [7.48 snapshots](../docs/validation/progress-snapshot-7.48.json).

Run `native/test-find.ps1 -BuildRoot <absolute-build-directory> -RunRoot <new-absolute-run-directory>` to build and exercise the actual Find dialog with an isolated three-record catalog. Use `-SkipBuild` only to reuse an explicitly chosen fixture executable.
