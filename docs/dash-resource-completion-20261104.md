# Completed DASH resource recovery, UDM 1.39.0

The resource store previously moved a completed payload to its .part name and then wrote the protected full receipt. A process exit or receipt-write failure in between could leave finished bytes without evidence that resource inspection could accept. Prefix recovery did not close this interval: a prefix checkpoint can describe an incomplete response and must not be treated as a completed segment.

DashResourceCommit now opens the completed staging file with read/write access, rejects redirected/non-file objects, checks its exact size and hashes the held file. Strong-prefix transfers also require agreement with their running digest. It flushes that file before writing a protected .commit.json intent containing a distinct completion kind, media-binding digest, bounded byte count, SHA-256 and a fixed staging discriminator. No arbitrary filesystem path is accepted from the marker. Payload promotion and full-receipt publication follow the intent.

[Microsoft documents FlushFileBuffers's write-access requirement and flush behavior](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers), and [MoveFileExW's replacement/write-through options](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw). The implementation preserves the existing same-folder move and protected atomic-metadata writer. These APIs and source ordering do not independently prove power-loss durability on every device/filesystem.

Resource inspection first accepts an existing verified full receipt as before. Otherwise it examines the protected completion intent and its bounded atomic-write scratch file. Each must identify the current binding, exact allowed staging kind and a valid full-resource size/hash. A current range binding requires its requested byte count; an unranged version binding requires its fixed entity size. Inspection hashes a regular staged .part.tmp/.resume file or the already-promoted .part file. Matching bytes can then finish the normal full-receipt publication without HTTP. Interrupted read/prefix metadata lacks the completion kind and is not accepted as completion evidence.

This inspection is also used by offline recording reconciliation and sealing. A recovered full receipt can therefore be promoted through the existing committed-resource checks without issuing another network request. The recording's normal interval, version and selection checks still apply. The marker attests successful transport-body completion and verified stored bytes; it does not prove per-segment media duration, content authenticity or playback.

The download path tracks entry into completed-resource publication. A subsequent local hash/flush/intent/move/receipt error preserves the finished staging and surfaces the error instead of deleting that body or downloading another alternative. The next inspection can recover only when a valid completion marker exists; an error or crash before that evidence is written can still require prefix reuse or refetching. Legacy bodies without the new marker are not retroactively considered complete.

After a full receipt has been verified or successfully published, best-effort cleanup removes only known regular internal files for that digest: completion markers/scratch, receipt scratch, old .part.tmp and prefix payload/metadata/scratch. Committed .part and .receipt.json files are excluded. Digest keys and fixed suffixes constrain paths to the intended recording directory; reparse points are skipped/refused. Cleanup failures do not invalidate a good complete receipt. This also removes obsolete generic temporary bodies left by earlier attempts after a successful recovery.

Same-directory concurrent writers and filesystem/path mutation remain unqualified. File verification releases its handle before the existing path-based move, so this is not a claim that every possible local filesystem race is eliminated. Permissions, locks, metadata corruption, flush failures, abrupt termination at each boundary, cancellation, reconciliation, stop-and-save and real device behavior require runtime acceptance. Additional verification/flush work has not been benchmarked.

No tests, installer creation, installation or publication were performed. Native version is 1.39.0; unchanged browser source remains 0.63.85. Full IDM parity, semantic CMAF-chunk salvage and validator-free/growing-resource recovery remain incomplete. See [source record](reference/dash-resource-completion-20261104.json) and [build receipt](validation/dash-resource-completion-build-20261104.json).

The production-only build completed with exit code 0. UDM, NativeHost, Monitor, SetupHelper and Automation all report 1.39.0; sizes and SHA-256 hashes are recorded in the receipt. The recorded source hashes remained unchanged during the build. This establishes compilation and artifact versions, not crash/reconciliation or filesystem-fault acceptance.
