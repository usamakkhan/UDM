# Windows FTP static bypass candidate, 7 October 2026

UDM previously rejected an FTP URL under “Use Windows proxy / PAC settings” whenever any Windows proxy setting was configured, even when a static proxy bypass rule matched that FTP host. The local candidate now selects direct FTP for an unconfigured Windows proxy or a matching static bypass. A Windows-configured PAC URL is passed to the existing FTP PAC resolver, which can select supported direct, SOCKS, and HTTP CONNECT routes. Automatic PAC/WPAD presence still prevents the static-bypass shortcut; auto-detect without a script URL now uses the asynchronous resolver.

The isolated native connection suite passed 395 checks, including assertions for matching bypass, Windows PAC URL precedence, nonmatching proxy, and WPAD rejection. The existing local transport fixture passed 24 checks, including FTP PAC transfer through the selected proxy for both control and data. This combines a Windows-settings policy-unit check with a real explicit-PAC transport check; it does not prove an actual Windows-configured PAC setting was read on this machine. The broader FTP proxy modes in [the backend audit](backend-idm-gap-audit-20261006.md) remain open. No installed application or personal proxy settings were changed.

On 7 October, the installed IDM 6.43 Connection options were inspected read-only. They showed eight default connections and a per-server exception list. UDM already has both behaviors, so no duplicate connection-policy change was made. UDM's FTP follow-up routes Windows auto-detect through WinHTTP's asynchronous proxy resolver when no explicit PAC URL is configured. Cancellation closes the resolver; discovery failure rejects the transfer without guessing a direct route. This is an implementation based on Microsoft's documented API, not a measured IDM FTP/WPAD transfer; live WPAD acceptance remains open.

The first isolated native test build at `candidates/ftp-wpad-20261007/build/release-native` compiled successfully. Its first test run stopped after 98 passes because the isolated build lacked FFmpeg helpers. After copying the repository's existing test helpers into that build, the rerun finished with 2,556 passes and zero failures. A subsequent source change replaced the synchronous discovery call with the existing asynchronous resolver. Its fresh native rerun passed 2,557 checks with zero failures, including the two new WPAD routing and pre-discovery cancellation checks. No Windows WPAD deployment was available for an end-to-end FTP auto-detect run.

A later follow-up normalizes whitespace separators in Windows FTP static bypass lists before matching hosts; WinHTTP documents both whitespace and semicolon separators. At that stage, unmatched static FTP proxy entries remained rejected because Windows can designate FTP-specific gateways that are not equivalent to UDM's supported SOCKS or HTTP CONNECT tunnels. Two focused bypass assertions cover matching and unrelated whitespace-separated rules. That isolated native build passed 2,559 checks with zero failures; its full output is in `candidates/ftp-wpad-20261007/native-suite-bypass.log`.

The next candidate recognizes the explicit Windows `ftp=http://host:port` proxy entry and routes it through UDM's HTTP CONNECT transport. The proxy must permit CONNECT to the FTP server's port; a rejected tunnel produces an error. Unlabeled entries, FTP gateway schemes, and duplicate FTP entries are not reinterpreted as CONNECT routes. The final native suite passed 2,562 checks with zero failures, including three new mapping assertions. The local transport fixture passed 24 checks with zero failures, including FTP control and data through CONNECT. The Windows source setting itself was not changed or exercised on this machine.
