# UDM 9.80: enforce server checksums on form downloads and their redirects

UDM 9.80 rejects native form-download responses whose selected server SHA-256 does not match the received bytes. It also collects the checksum on the GET following a form redirect, and rechecks retained responses after Resume/catalog reopening. Both extension source manifests advance to 0.73.44; browser JavaScript is unchanged. Five native programs build as 9.80. This candidate is **uninstalled**; overall IDM speed and UI parity remain open.

## Confirmed defects and fix

The direct POST reader already saved `ServerSha256`, but the ordinary publication gate excluded jobs with a POST request. A form redirected to GET also omitted the hasher argument that enables response-checksum collection. These were separate breaks in the same verification path.

Seven frozen 9.79 cases published despite mismatched declarations: direct `Repr-Digest`, `Content-Digest` and legacy `Digest`; 303-to-GET; 307 repost; an empty body; and a body without a declared length. Two matching-checksum controls completed correctly. Each reproduction retained its actual status, published hash, stored checksum and exact request count rather than treating the expected failed assertion as a passing test.

[Transfer.cpp](../native/Transfer.cpp) now passes the existing hasher through both form-to-GET paths and applies the selected full-body checksum to single-file POST results. Fresh ordinary POST already hashes inline; this change does not add another body read there. Cached/required verification retains its existing file ownership and integrity gates. No source data, required digest, durable publication barrier or form-replay rule is removed.

For 204/205 replies, representation/legacy digest metadata can describe bytes other than the empty message body. The POST reader therefore does not treat those fields as an empty-file checksum; a `Content-Digest` still checks the actual body. Fresh 200/201/204/205 controls cover these distinctions. The [digest specification](https://www.rfc-editor.org/rfc/rfc9530.html#appendix-B.7) distinguishes POST request/response representations and [no-content representation metadata](https://www.rfc-editor.org/rfc/rfc9530.html#appendix-B.9). This change preserves the existing SHA-256 parser and field precedence; it does not claim complete digest-field or trailer support.

## Actual HTTP and recovery qualification

All **1,559 assertions in 23 affected backend suites** pass. The maintained [plain form fixture](../native/HttpPostIdentityTests.cpp) and [owned origin runner](../tests/http-post-identity.native-live.cjs) add a selected checksum mode:

| Candidate flow | Native checks | HTTP request audit |
| --- | ---: | --- |
| Twenty-one checksum cases on D: | 88 | Exactly 25 requests; no retry/reopen replay |
| Same twenty-one cases on C: | 88 | Exactly 25 requests; no retry/reopen replay |
| Existing plain-form workflows | 53 | Existing one-use/explicit-restart counts preserved |
| Existing gzip-form workflows | 49 | Existing one-use/explicit-restart counts preserved |

The 278 workflow assertions are separate from the backend count. Cases cover correct and mismatched supported fields, empty and unknown-length replies, 201 Created, 303-to-GET, 307 repost, and no-content metadata. Every mismatch stays Failed and unpublished. The nine rejected cases per drive preserve their raw response, reopen their catalog, reject again from verified saved bytes and leave those bytes unchanged. Reopening adds no HTTP request. Successful outputs match independently generated hashes. Existing workflows retain exact pre-Start size, prefix stripping, collision/journal recovery, Download Later, changed-context rejection and explicit-only resubmission behavior.

The maintained checksum mode is selected with `UDM_POST_DIGEST_CASE=all` while `UDM_POST_IDENTITY_TEST_EXE` points at the built fixture. The ordinary mode remains unchanged when that variable is absent. Integration fixtures already have explicit selection support in the native build script; no new default-suite entry is needed.

## Legacy saved responses and gzip byte domains

Two fresh catalogs are generated by the frozen 9.79 worker, with a complete response retained after an intentionally wrong user checksum. Removing only that user checksum lets 9.79 publish despite the still-wrong server checksum. Resuming the other 9.79-created catalog with 9.80 rejects the same response class, preserves its raw hash and reuses the receipt. Only the two original capture POSTs occur; neither Resume submits again. This verifies a legacy nonempty 200 response, not migration of every historical response/status combination. Unmatched retained digests remain blocked rather than silently discarded or automatically resubmitted.

Separate gzip controls compare four old and four current flows. The advertised checksum is over 71 encoded bytes; the published file is 1,517 decoded bytes with a different independent hash. Both matching candidate responses publish the decoded file. Both mismatches remain unpublished and retain the existing invalid-wire receipt policy. The old direct gzip path already rejected a mismatch; the old redirected gzip path ignored the declaration and published. 9.80 corrects that redirected case. These are byte-domain correctness checks, not speed measurements.

The supplementary gzip controller initially required the old matching redirected response to have a stored checksum. Its missing field is the defect under investigation. The assertion expectation was corrected without changing product code: all three already completed flows were recovered from their recorded outputs, and only the five unfinished flows ran. Original controller, correction, source hashes, initial/resumed server logs and every result remain in evidence.
