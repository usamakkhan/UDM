# Two-producer File Info ownership — 8.36 / browser 0.72.0

## Behavior

The 8.35 join path followed a matching in-flight receipt, but its fixture did not publish a second browser-owned File Info view. This increment handles overlapping validated producers inside the same inbox. A retained rejected/uncertain presentation, or a presentation whose explicit Retry is active, can receive a new prepared successor for its exact receipt token. The Manager must already have validated the token and request fingerprint before invoking this in-process sink. No new wire protocol or browser-side trust decision is introduced.

The successor shares the original session and takes its active/private presentation claim. It does not post another window notification. If the original posted key is still undispatched, its inbox entry is retargeted to the successor so suppression cannot leave the user without a dialog. If the original dialog is already open, its normal pulse follows the session's current operation while retaining its HWND and edited fields. Untagged deliveries remain independent. Settled accepted or attached presentations cannot be replaced by an unproven prepared identity.

Retry activity is session-wide. A second producer cannot enable another Retry while the original retry worker is still resolving ownership. Superseded/retired operations are not eligible to retry, even after their weak current-operation reference expires. A matching accepted successor is reused by the joined worker; the worker does not finish another producer's ticket. Definite producer failure can still yield to the already requested Retry, and its new prepared identity replaces the rejected successor without retaining an old active claim.

Cancel follows the current operation through the shared session. While an explicit Retry is active, the cancellation worker waits for that session's outcome; once a durable accepted identity is known, it performs the normal safe cancellation and receipt-presentation cleanup. No UI handler waits for the held write. State and session locks nest only in State → Session order; cancellation releases the session lock before waking State. Successor allocations finish before the previous claim is retired.

The expanded backend fixture exercises two independent prepared-view producers against the actual Manager admission path, with gates before the second inbox publication and before its temporary-file write finishes. It covers both competing outcomes, shared Retry exclusion, one notification, cancellation, reuse of the accepted producer identity and the second producer's ticket lifetime. Separate inbox checks cover the undispatched original key, settled/attached rejection and independent untagged messages. The UI fixture adds notified success/rejection/cancellation in light and dark modes while checking the same HWND, draft, hidden main owner and cancellation before the second write is released.

These are owned native fixtures, not installed-browser acceptance. Full browser worker restart/reconnect, quality/container coverage, Windows session-end, and a fresh submission after the original cancelled session has completely retired remain separate gates. In particular, this in-memory coalescing does not introduce a new durable cancellation tombstone. Finishing-delay parity and kernel IO attribution remain unresolved, and no new IDM performance comparison is claimed.
