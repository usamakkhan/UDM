# Durable pending cancellation — 8.37 / browser 0.72.1

## Ownership and persistence

In 8.36, cancelling a rejected pending File Info offer could finish after finding no live job, without saving a missing-receipt barrier. A later replay after the inbox retired could therefore be treated as a new media admission. The 8.37 source adds a Manager-owned cancellation operation rather than interpreting the dialog's disappearance as a durable decision.

The immutable initial view now carries the validated request fingerprint separately from its render projection. The inbox session retains this private binding through retries and notified successors. It is not a control value, a wire field or a plaintext durable receipt. Rendering-cache comparison still compares render inputs; session replacement and cancellation check ownership independently. A successor with a conflicting nonempty fingerprint cannot inherit the old dialog session.

The background cancellation owner handles three cases under the Manager lock. An accepted receipt must have the same fingerprint; only its still-unconfirmed live job can be removed. Start/Download Later and other user-confirmed state are preserved. A matching in-flight reservation is observed outside the Manager lock through live installation or terminal ownership failure, followed by durable/live revalidation. If neither receipt nor reservation exists, the Manager saves a protocol-3 released receipt with the existing retention rules before cancellation succeeds. A published-but-unreconciled admission remains an error, never permission to overwrite its outcome.

The released receipt contains only token time, protocol, status and the cancellation marker. Accepted receipts retain their accepted identity after pending-job removal. Wrong protocol, changed fingerprint and failed writes remain errors; they do not remove unrelated history or acknowledge a release that was not persisted. Existing unbound/internal views retain the older exact-job cancellation fallback.
