# Missing saved files during removal — UDM 1.46.0

The retained IDM removal handler at 0x00470380 checks GetFileAttributesA/W before its optional completed-file Shell deletion. An invalid attribute result skips that filesystem branch, while the approved record still proceeds to the list deletion call carrying LVM_DELETEITEM (0x1008). UDM's combined workflow instead called strict recycleCompleted first and aborted catalog removal when the saved path had already disappeared. This prevented the completed-history removal already approved by the user.

Manager::recycleCompleted now has an explicit allowMissingForRemoval argument, defaulting false. Only the default recycle callback in removeDownloadSelection passes true. After the existing scoped file/replacement recovery and dependency checks, the method requires an absolute target and queries its attributes. If Windows reports ERROR_FILE_NOT_FOUND or ERROR_PATH_NOT_FOUND, combined removal returns from the recycle step without creating a Shell operation, RecyclePending intent, RecycledAt timestamp or File recycled status. The caller then performs the already-approved Manager::remove with its expected-completion check. Native history-save failure handling and post-body cleanup remain on that path.

Standalone Recycle downloaded files and existing two-argument callers retain strict behavior. An unavailable file still reports an error there. Other attribute failures, including reported access, device or network errors, retain the history record and include the Windows error number. Directory and reparse-point targets remain rejected. The reporting policy uses the error returned by the filesystem; it does not independently prove physical absence under arbitrary mapped-drive, mount, redirector or driver behavior. A disappearance after preflight or a Shell cancellation/error still follows the existing failure path rather than becoming inferred recycle success.

Before any recovery or file deletion, recycling now requires the JobPtr to still belong to Manager::jobs. Membership, activity and Complete state are checked again after recovery. This closes the stale completed-pointer path, where an already-removed record could previously reach the filesystem operation. Existing active-transfer, replacement-dependency and regular-target protections remain. Successful ordinary recycling still requires the existing sink and Windows confirmation; permanent deletion fallback remains excluded.

The narrower Win32 error classification is deliberate: the inspected reference skips its attribute branch for any invalid result, whereas UDM preserves its existing error/record-retention policy outside the two reported not-found codes. [Microsoft's attribute API](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileattributesw) specifies using GetLastError after failure, and its [system error definitions](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--0-499-) distinguish missing file/path from other failures. The reference's ignored Shell-result and directory handling are not copied by this increment. Full error-path equivalence remains unfinished.
