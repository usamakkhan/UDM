# Strong-date DASH prefix resume — UDM 1.41.0

The 1.38.0 prefix implementation required a strong ETag. A server that supplied Last-Modified but no ETag therefore could not retain an interrupted whole-resource prefix, even when its response contained evidence allowing a strong date validator. This change connects that case to the existing checkpoint, If-Range and full-response fallback paths.

RFC 9110 [8.8.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.2.2) permits a client to infer date strength from a stored response's Date/Last-Modified separation and sufficient clock evidence. Its minimum is one second with the stated clock qualification. UDM uses a more conservative 60-second separation policy where clocks may be generated independently; this is an implementation inference, not proof against arbitrary server clock skew. The local PC's time is not used. Section [13.1.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5) forbids date-based If-Range when the client has an entity tag. A weak, malformed, empty or duplicated ETag therefore does not permit date fallback.

The response selector prefers a single valid strong ETag. Only responses with no ETag field can select dates, requiring exactly one Last-Modified and one Date, complete bounded HTTP-date syntax, successful Windows date/calendar conversion and at least 60 seconds between them. IMF-fixdate and the two obsolete HTTP-date syntaxes are recognized before Windows conversion; unsupported or invalid dates simply prevent prefix retention. Calendar normalization is checked by a FILETIME round trip. Weekday-label equivalence and obsolete-year interpretation remain delegated to WinHTTP and are not independently qualified.

Protected checkpoint bodies keep the existing ETag field. Date checkpoints store it empty and add lastModified and responseDate. The saved evidence is validated again when loading. Existing strong-ETag checkpoints remain readable; old builds ignore date checkpoints because they lack a strong ETag. No published full-resource receipt format or media-binding identity changes.

After exact-URL and held-file prefix hash verification, the saved validator supplies If-Range alongside Range. An appended 206 must have the same validator kind and exact saved value. Date mode requires a fresh qualifying date pair and still no ETag; a newly introduced tag causes full-fetch fallback rather than crossing validators. Date evidence can advance while the Last-Modified value remains identical. A full 200 response resets the prefix instead of appending. Invalid 206, 412 and 416 responses retain the existing one-time unconditional retry policy.

The exact Content-Range start/end/total, declared remaining length, identity encoding, multipart rejection, periodic flushed SHA-256 checkpoints and final whole-resource completion checks remain. Byte-range/version-bound shared resources remain outside prefix resume. Changed URLs, insufficient or missing date evidence and weak validators may still require a full fetch. Full-resource completion remains distinct from merely reaching a checkpoint's declared length.

All five production native targets built successfully (exit code 0) and report 1.41.0. Their sizes and SHA-256 hashes are recorded in the [build receipt](validation/dash-date-resume-build-20261104.json); the captured source hashes remained unchanged. The [protocol/source evidence](reference/dash-date-resume-20261104.json) records the scope. Runtime/parser/network tests, installation, installer creation and publication are deferred. This is transfer-source work, not an observed IDM implementation or proof of full parity.
