# Video handoff and progress-window behavior

Selecting a YouTube format previously waited for the native direct-link lookup's full ten-second deadline before using an already captured browser stream. The selection now gives the direct pair two seconds to arrive. If a usable captured stream is available afterward, it proceeds through the existing handoff. If there is no usable capture, it still awaits the original bounded lookup rather than discarding a potentially valid result.

The lookup does not create a download. Only the final, document-validated selection is submitted, so a late lookup response cannot add a second job. Available direct browser links remain immediate and final document, video, format, and transport checks remain in place. This reduces one source of delay; it does not promise a two-second total handoff or faster SABR transfers.

Manually started video jobs now open their progress window normally instead of inheriting a minimized/tray startup mode. Scheduled queue jobs retain the explicit queue preference. New queue settings default to a normal progress window; existing saved queue preferences are retained. Explicit suppression of progress dialogs still applies, and users can minimize a window after opening it.

Validation: 29 transport-handoff checks pass against each of the Chromium and Firefox sources, including a direct pair arriving after 1.2 seconds, slow lookup with a captured fallback, late-reply duplicate prevention, document changes, and continued waiting when no captured stream exists. All 56 browser checks also pass. The native C++/MFC application build completed successfully using `native/build.ps1 -AppOnly` with an isolated output root on C:. These are source regressions and compilation checks, not a fresh completed download or live dialog verification in the user's browser. The staged app has not replaced the installed executable; the browser extension also needs reloading for these source changes to take effect.
